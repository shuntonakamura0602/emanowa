## えまのわ — Codex向け実装仕様書 v1.0

作成日: 2026-10-28 / 対象: 日本語利用者向けWebサービス / 表示時刻: Asia/Tokyo

### この仕様書の使い方

**えまのわは、100万枠の共有空間に自分の絵馬を掛け、みんなの願いを眺め、友達を近くに招けるサービスである。**

このフォルダをリポジトリの `docs/spec/` に置き、Codexには最初にこのファイルと `08_CODEX_PROMPTS.md` を渡す。最初の実装対象は **P0**。P1/P2をまとめて実装する必要はない。各段階で動く機能を増やし、受け入れ条件を満たしてから次へ進む。

これは実装前の仕様書であり、アプリの完成、デプロイ、負荷試験の実施を示すものではない。数値目標は実装時に検証する目標である。

仮置きの価格・日程は設定値にする。取得済みドメイン、商標登録済み、神社との提携、宗教上の効力があると表示しない。運営情報が未入力でもローカル開発は進め、本番公開時に必要項目を検出する。

### 全パート共通の契約

1. **100万枠は論理上の場所。** 1000×1000、座標は0〜999、表示番号は `y * 1000 + x + 1`。空白100万行・100万DOM・全件JSONを作らない。
2. **年ごとの場を持つ。** 例は `worldSlug = "2027"`。過年度のURLはその年のまま保持する。現在の西暦だけで表示先を決めない。
3. **1アカウント・1年度につき1枚。** `active` または `hidden` の絵馬を1枚まで。匿名利用者も内部では認証UIDを持つ。同じ人の別端末を厳密に識別する仕様ではない。
4. **公開URLは絵馬に結びつく。** `/w/{worldSlug}/e/{publicId}`。枠の番号を永続的な作品IDにしない。削除後に場所を再利用しても古いURLは別の人の絵馬にならない。
5. **投稿完了時に枠を確定する。** 選択中の場所は予約ではない。同時投稿の負け側には409を返し、近隣候補の再取得へ案内する。願いの下書きを保持する。
6. **本文と一覧掲載を分けて扱う。** `visibility = public | unlisted`、`message_visibility = public | owner_only`。URL限定は認証付き非公開ではない。本人だけの本文は公開API・HTML・画像に含めない。
7. **本文は80、名前は20 graphemeまで。** 日本語・絵文字を意識し、フロントとサーバーで同じ数え方にする。HTMLは受け付けず、プレーンテキストとして描画する。
8. **本番の保存先はDB。** 一時メモリー、ブラウザだけ、偽の成功画面を本番用データ永続化として扱わない。モックは開発専用として明示する。
9. **P0は軽い2D体験。** テキストと絵馬テンプレート、パン・ズーム可能なCanvas、代替の一覧表示。手描き・画像投稿・AI・3D/VRは含めない。
10. **課金と団体機能は段階的に開く。** `ENABLE_GROUPS`、`ENABLE_FULFILLMENT`、`ENABLE_PAYMENTS` は初期値false。サーバーが機能の可否を決める。
11. **共有は利用者が実行する。** XやLINEへの自動投稿、連絡先取得、勝手な招待送信を行わない。共有ボタンから投稿・送信画面を開く。
12. **登録なしで始められ、後から復元手段を追加できる。** 閲覧では匿名アカウントを作らない。書き始めた利用者にゲスト所有権を用意し、任意のメール確認で同じUIDに紐づける。

### 実装の境界

| 段階 | 提供する体験 | 完成の考え方 |
|---|---|---|
| P0 | 書く、掛ける、眺める、編集・削除、共有、近くに招く、通報 | 別ブラウザから同じ絵馬が見え、本人以外は変更できない |
| P1 | 無料グループ、願いが叶った記録 | P0の所有権・公開範囲を壊さず追加できる |
| P2 | 有料デザイン、主催者向け機能 | 決済確認、権利付与、重複・返金処理が整合する |
| P3 | 手描き、物品、協賛、提携、3D等 | 利用実績を見て別仕様を作る |

P0に必要な通報・削除・権限制御・復元導線を「後で付ける」として省略しない。一方、P2のDBや画面を先に作り込む必要はない。

## Part 01 — プロダクト・対象範囲

### 1. 提供するもの

名称は **えまのわ**。日本語で願い事を書いた絵馬を、年ごとの大きな共有空間に掛けられるWebサービスとする。

説明文の初期案は「みんなの願いが集まる、オンライン絵馬。」。トップの主見出しは「あなたの願いを、ここに。」、主ボタンは「絵馬を書く」。説明やボタンで「claim」「plot」「ウォレット」等の用語を利用者に要求しない。

初めての訪問でも、「何をする場所か」「無料で始められること」「願いが誰に見えるか」が分かる。最初の投稿に住所・本名・電話番号・決済登録は求めない。

### 2. 目標体験

1. SNSや友達のURLから入る。
2. 共有空間の絵馬を眺め、自分も参加できると分かる。
3. 願いと任意の名前を書き、絵馬の見た目と公開範囲を確認する。
4. 空いている場所を選び、投稿を確定する。
5. 自分の絵馬がその場所に掛かり、URLと共有画像が得られる。
6. 「近くに絵馬を掛けてもらう」招待を送り、友達が同じ周辺に参加できる。
7. 後日、自分の絵馬やその周辺を見に戻る。

場所選びは任意に迷える楽しみを残しつつ、「この近くに掛ける」「空いている場所を選ぶ」で短く済ませられる。送信前に自分の絵馬を確認できる。

### 3. 対象利用者

| 利用者 | 主な動機 | 提供する価値 |
|---|---|---|
| 個人 | 新年の抱負、試験、仕事、健康、家族への願い | 一枚を残し、場所を共有する |
| 友達・家族 | 近くに並べたい、互いの願いを見たい | 近隣への招待、簡単な共有 |
| 小さなコミュニティ | 同じテーマの願いを集めたい | P1の無料グループ |
| イベント主催者 | 参加者と一つの景色を作りたい | P2の見た目・展示・集計機能 |

日本語UIを優先する。年齢や専門知識を前提にしない。願いには個人的な内容が含まれ得るため、投稿前の公開範囲と削除導線を基本機能とする。

### 4. 初期版の機能（P0）

| ID | 機能 | 必須の振る舞い |
|---|---|---|
| P0-01 | トップ・説明 | 無料の参加導線、現在受付中の年度、実データに基づく件数 |
| P0-02 | 世界の閲覧 | パン・ズーム、全体を見る、中心へ戻る、絵馬一覧へ切替 |
| P0-03 | 絵馬作成 | 願い80文字、名前20文字、分類、無料テンプレート、プレビュー |
| P0-04 | 場所選択 | 指定場所・近隣候補、競合時の再選択、下書き保持 |
| P0-05 | 所有と復元 | ゲスト所有、本人の絵馬へ戻る、任意のメール連携・再ログイン |
| P0-06 | 個別ページ | 絵馬、場所、共有、地図で見る、近くへの招待 |
| P0-07 | 編集・削除 | 本人のみ、版番号で競合検出、削除後は公開内容を返さない |
| P0-08 | 公開範囲 | 地図への掲載、本文の公開を別々に設定 |
| P0-09 | 共有 | X、LINE、URLコピー、PNG保存、OG画像 |
| P0-10 | 探索 | 公開絵馬の新着・分類・ランダム、カーソル式一覧 |
| P0-11 | 通報・管理 | 理由付き通報、運営による非表示・復帰、操作記録 |
| P0-12 | 基本運用 | 利用規約、プライバシー説明、問い合わせ、障害・空状態 |

P0では「いいね数」「順位」「他人へのコメント」「DM」「通知メールの自動配信」を作らない。利用者同士のやり取りは共有や隣への参加を中心とする。

### 5. P1以降

#### P1 — 仲間と続ける

- 無料グループ: 同じ年度・10×10の範囲を目印に願いを集める。場所の独占予約ではない。
- 一枚につき所属グループは最大1つ。主催者が他人の絵馬の所有者になることはない。
- 「願いが叶った」の記録: 本人が状態を変更する。詳細の公開範囲は元の絵馬に従い、新しい本文・写真機能は足さない。

#### P2 — 収益化

- 有料の絵馬デザイン。
- グループの主催者向けの表示・集計・出力機能。
- 支払処理、返金、購入者の復元、運営表示を含む。金額と商品範囲は06の初期案を採用する。

#### P3 — 別途検討

手描き、画像投稿、AI補助、実物の絵馬・ポスター、協賛、神社との提携、3D/VR、毎年の自動リマインド。仕様がないものを先回りで実装しない。

### 6. 世界と年度の運用

#### 6.1 年度ごとの独立性

`worldSlug` は表示用の安定ID。初期案は西暦4桁。2027年の絵馬と2028年の絵馬は異なる場に存在し、各年度で1枚ずつ持てる。枠の総数は各年度100万。売却・譲渡・転売の機能は持たない。

トップはサーバー設定の `featured_world_slug` を使う。12月に翌年の場を開けるため、`new Date().getFullYear()` のみで決めない。過年度ページは元のURLを維持する。

#### 6.2 状態

| 状態 | 閲覧 | 新規・本文編集 | 削除・公開範囲縮小 | グループ参加 |
|---|---|---|---|---|
| preview | 可。受付前と表示 | 不可 | 既存データがあれば本人のみ可 | 不可 |
| open | 可 | 本人・空き枠等の条件を満たせば可 | 本人のみ可 | P1有効時に可 |
| archived | 可。受付終了と表示 | 不可 | 本人のみ可 | 不可 |

公開範囲の縮小は `public → unlisted` と `message_visibility: public → owner_only`。archivedでは逆方向の変更、名前・分類・デザイン・叶った状態の変更も行わない。削除と非表示の管理操作は引き続き可能とする。P2の返金等による権利取消と標準外観への復帰は、一般編集とは別のシステム処理として06に従う。

受付期間は `opens_at <= now < closes_at` の半開区間で、サーバー時刻を用いる。DBはUTC、UIはJST。管理上の停止が必要な場合は受付を止める設定を持ち、時刻だけで停止を上書きしない。

#### 6.3 初期データ案

| 項目 | 提案値 |
|---|---|
| slug | 2027 |
| 名称 | 2027年のえまのわ |
| 受付開始 | 2026-12-20 00:00 JST = 2026-12-19T15:00:00Z |
| 受付終了 | 2028-01-01 00:00 JST = 2027-12-31T15:00:00Z |
| 一辺 | 1000枠 |
| 初期注目座標 | x=500, y=500 |

この日程は発売日・公開日を確約するものではない。開発用seedは固定した検証時刻を使い、テストが現在日付に依存して投稿不能にならないようにする。本番に架空の参加者や願いをseedしない。

### 7. 投稿内容と公開設定

- 願いは必須、1〜80 grapheme。空白だけを拒否する。
- 名前は任意、0〜20 grapheme。未入力は「ななしさん」等の表示名をUIで補う。実名は求めない。
- 分類は `family / health / study / work / love / challenge / other`。それぞれ「家族」「健康」「学び・合格」「仕事」「恋愛・ご縁」「挑戦」「その他」。
- P0は無料デザイン `basic_wood` を1種用意する。後から追加するデザインも色だけに意味を依存させない。
- 投稿中の願いを外部AIや解析サービスに送らない。
- HTML・Markdown埋め込み・外部画像を許可しない。URLはP0ではリンク化しない。

| 設定 | 他の人の地図・一覧 | URLを開いた人 | 本人 |
|---|---|---|---|
| public / public | 公開絵馬として表示 | 本文を表示 | 表示・編集 |
| public / owner_only | 公開名・絵馬の外観。本文なし | 「ひみつの願い」と表示 | 本文を表示・編集 |
| unlisted / public | 場所は使用中とだけ表示 | 本文を表示 | 表示・編集 |
| unlisted / owner_only | 場所は使用中とだけ表示 | 「ひみつの願い」と表示 | 本文を表示・編集 |

URL限定でもリンクを知る人は閲覧できる。名前の公開範囲は本文と別であり、「ひみつの願い」でも入力した名前が見えることを設定画面に書く。完全なログイン制の私的保管庫は初期版の範囲外。

### 8. 所有者・運営・主催者の違い

| 役割 | 権限 |
|---|---|
| 閲覧者 | 許可された公開情報を閲覧する |
| ゲスト所有者 | 自分の絵馬の作成・編集・削除。復元は現在の認証情報がある間 |
| メール確認済み所有者 | 同じ所有権を保持し、別端末で再ログインできる |
| P1グループ主催者 | グループ名・募集状態・所属リストを管理する |
| 運営管理者 | 通報対応、絵馬の非表示・復帰、受付の停止。すべて記録する |

管理者向けにも本人だけの本文を通常画面で出さない。調査に必要な特別アクセスを後から加える場合は別の権限と監査を仕様化する。グループ主催者に他人の本文編集・削除・秘密の本文閲覧を与えない。

メール未連携のゲストがログアウトしたりブラウザの保存情報を消した場合の所有権復元は保証しない。この説明と任意のメール連携を投稿完了後に示す。メールアドレスを知っているだけで所有者を切り替えない。

### 9. 成功の測定

最初に見るのは「自分の一枚を掛けられたか」「共有先の人が参加したか」「再訪したか」。以下は集計定義であり、売上・拡散率の予測ではない。

| 指標 | 定義 |
|---|---|
| 作成完了率 | サーバーで成功した作成数 ÷ 作成画面の開始数 |
| 場所競合率 | `SLOT_TAKEN`件数 ÷ 作成要求数。送信再試行は区別する |
| 共有操作率 | 投稿完了後に共有ボタンを使ったセッションの割合 |
| 招待参加 | `near`を起点とする流入から作成完了した件数 |
| 再訪 | 同意・設定に沿って識別できる範囲の再訪。端末をまたぐ完全追跡はしない |
| 運営負荷 | 通報件数、未処理件数、DB・画像生成の費用、APIエラー率 |

共有ボタンのクリックを「X投稿完了」「LINE送信完了」と数えない。公開本文・ニックネーム・メール・トークン・秘密のURL全体を解析イベントに含めない。公開カウンターは実データから計算し、満席感を出すための水増しをしない。

### 10. P0のプロダクト受け入れ条件

初めての利用者がスマートフォンで、アカウント登録画面を強制されずに一枚を掛けられる。別のブラウザでそのURLを開くと公開設定に沿って表示され、近くへの招待から別の一枚を掛けられる。元の所有者は自分の絵馬を編集・削除でき、他人は変更できない。大量の空白枠を読み込まずに100万枠を探索できる。

これに加え、07の権限・同時投稿・キャッシュ・実機表示・復旧手順の条件を満たしてP0完了とする。

## えまのわ 画面と操作仕様

このパートは、日本語の画面、利用者の操作、入力項目、エラー時の動作を定義する。原則として P0 の必須仕様を扱う。地図の描画・座標計算は `03_WORLD_AND_PLACEMENT.md`、所有権と保存処理は `04_DATA_AUTH_API.md`、共有と P1 の共同エリアは `05_SHARING_AND_GROUPS.md` に従う。

### 1. デザインの基準

- 主な利用端末はスマートフォン。幅 360 CSS px から横スクロールなしで操作できること。
- 画面は日本語。日時は `Asia/Tokyo` で表示する。
- サービス名は「えまのわ」。説明文は「みんなの願いが集まる、オンライン絵馬。」を基本とする。
- トップの主見出しは「あなたの願いを、ここに。」、主ボタンは「絵馬を書く」。
- 世界は木の絵馬が並ぶ穏やかな共有空間として表現する。参拝・祈祷の効果を約束する表現は使わない。
- P0 は文字を書ける 2D の絵馬。手描き、画像アップロード、音声、3D、VR の操作は表示しない。
- 操作の主語は「書く」「掛ける」「眺める」「近くに招く」。利用者向け画面には claim、mint、RPC、座標チャンク等の実装用語を出さない。
- 本物の参加者数と実際の絵馬を表示する。開発用サンプルには「サンプル」と表示し、本番の件数に含めない。

#### 1.1 視覚トークンの初期値

以下は初期デザインの指定値。実装時にコントラストを測定し、アクセシビリティの基準を満たすよう調整する。

| 項目 | 初期値・方針 |
| --- | --- |
| 背景 | `#F7F1E5` |
| カード | `#FFFDF8` |
| 本文 | `#2C2926` |
| 補助文字 | `#665D53` |
| 主ボタン | `#6D3B2E`、文字は白 |
| 成功・完了 | `#35684E` |
| フォント | 日本語対応のシステム sans-serif を基本にする |
| 本文サイズ | 原則 16px 以上 |
| 角丸 | 入力欄・カードは 12〜16px を基準に統一 |
| タップ領域 | 原則 44×44 CSS px 以上 |
| アニメーション | 掛け終わり・地図移動の短い演出。操作を待たせない |

絵馬の形や木目は同じデザインデータを地図、詳細、共有画像で再利用する。本文が読めなくなる装飾、極端に細い文字、常時点滅する演出は採用しない。

### 2. ページ構成

| ルート | 用途 | 主な表示 |
| --- | --- | --- |
| `/` | サービス入口 | 開催中の年の世界への入口、説明、自分の絵馬への導線 |
| `/w/{worldSlug}` | 地図・探索 | 絵馬掛け、地図/一覧切替、書くボタン、公開絵馬の探索 |
| `/w/{worldSlug}/new` | 新規作成 | 場所選択、願いの入力、公開設定、確認、確定 |
| `/w/{worldSlug}/e/{publicId}` | 絵馬の詳細 | 公開用絵馬、番号、共有、近くに掛ける、通報 |
| `/w/{worldSlug}/e/{publicId}/edit` | 本人編集 | 本人確認済みの内容、編集、公開設定変更、削除 |
| `/me` | 自分の絵馬 | 本人の年別一覧、編集、メール連携・復元案内 |
| `/about` | サービス説明 | 利用方法、公開範囲、運営への連絡先 |
| `/terms`、`/privacy` | 利用条件 | 公開前に確認する文書 |
| `/admin` | 運営者専用 | 通報一覧、絵馬の非表示、対応記録。ルートを隠すことを権限確認の代わりにしない |

`publicId` は UUID。表示番号と異なり、他人の作品や別の年へ付け替えない。`worldSlug` は `2027` のような年を表す設定値とし、画面に年をハードコードしない。

P1 のグループ公開ページは `/w/{worldSlug}/g/{groupPublicId}`。P0 ではグループ作成・課金への未完成ボタンを表示しない。`ENABLE_GROUPS`、`ENABLE_FULFILLMENT`、`ENABLE_PAYMENTS` はサーバー側で管理し、画面には必要な機能の利用可否だけを渡す。

### 3. 共通ナビゲーション

#### 3.1 モバイル

- 上部にロゴ、対象年、メニューを置く。
- 地図上に表示する主操作は「絵馬を書く」「自分の絵馬」「一覧」の三つを基本とする。
- 拡大・縮小と「いま見ている場所を共有」は地図専用の補助操作に分ける。
- 「全体を見る」「中心へ戻る」も地図の補助操作として用意し、戻る先を見失わないようにする。
- 最下部のボタンは端末の safe area と重ならない位置にする。
- 画面を占有する説明は初回だけ閉じられるカードにし、地図を常時隠さない。
- ソフトウェアキーボードが開いている間も入力と確定ボタンへ到達できること。

#### 3.2 デスクトップ

- 地図を主領域、絵馬の詳細や入力をサイドパネルまたは別ページにする。
- モバイルと同じ URL を使う。表示幅に応じた UI 変更で、別の保存処理を作らない。
- 詳細パネルを閉じると、直前に見ていた地図の位置に戻れること。

### 4. 世界を開いたとき

#### 4.1 初期表示

初期中心の決め方は次の順とする。

1. 有効な絵馬・招待・場所へのリンクがあれば、その対象を表示する。
2. URL に地図位置が明示されていれば、その位置を表示する。
3. 通常の入口では、公開絵馬が集まる表示候補をサーバーから取得する。
4. まだ絵馬がなければ、初期中心で空き枠と最初の投稿の案内を表示する。

通常の入口で、100万枠全体を最小倍率にしてから操作させない。最初は絵馬と空き枠を認識できる倍率にする。

#### 4.2 空の状態

- 文言例：「この場所に、最初の願いを掛けてみませんか。」
- 主ボタン：「絵馬を書く」
- 実際の投稿がない場所を、架空の願いで埋めない。
- 空き枠を選んでも、その時点では予約や所有を成立させない。

#### 4.3 公開絵馬の探索

- 地図と、キーボード・読み上げでも使える一覧を用意する。
- P0 の探索は「新しい絵馬」「カテゴリー」「ランダムに見る」を基本にする。ランダムの候補にも `active` / `public` の条件を適用する。
- 全文検索、人気ランキング、閲覧者同士のコメントは P0 に含めない。
- `unlisted` の絵馬は公開一覧に含めない。
- `owner_only` の本文は、カードの裏面・ツールチップ・アクセシビリティ用テキストにも出さない。
- 読み込み失敗時は空の世界として扱わず、「読み込めませんでした」「もう一度読み込む」を表示する。

### 5. 新しい絵馬を掛ける

#### 5.1 操作の順序

1. 空き枠を選ぶ、または「絵馬を書く」から空き枠候補を表示する。
2. 書き始める操作に合わせてゲストの所有セッションを準備する。
3. 願い、表示名、カテゴリー、公開範囲を入力する。
4. 地図での見え方・リンク先・共有画像を確認する。
5. 「この場所に掛ける」で保存を確定する。
6. 保存された作品を表示し、共有・近くへの招待・メール連携を案内する。

匿名セッションは閲覧だけでは作成しない。準備に失敗した場合、入力欄を失わず再試行できるようにする。

地図の空き枠から始める場合は場所を先に選べる。「絵馬を書く」から始める場合は文面を先に入力し、確認画面までに場所を決めてもよい。どちらも保存前に場所と公開範囲を確認する同じ確定処理へ合流させる。

#### 5.2 入力項目

| 項目 | APIキー（04を正本とする） | 入力規則 | UI |
| --- | --- | --- | --- |
| 願い | `wishText` | 必須、80書記素以内、空白のみ不可、プレーンテキスト | 「叶えたいことを書いてください」 |
| 表示名 | `nickname` | 任意、20書記素以内、未入力可 | 「表示名（任意）」 |
| カテゴリー | `category` | 下表のいずれか | 未選択は `other` |
| デザイン | `designId` | P0 は `basic_wood` | 無料の標準絵馬 |
| 掲載範囲 | `visibility` | `public` または `unlisted` | 二択 |
| 願い本文の公開 | `messageVisibility` | `public` または `owner_only` | 二択 |

文字数は見た目上の文字で数える。絵文字の組み合わせなどについてクライアントとサーバーで同じ数え方を使う。本文は最大4行、表示名は1行とし、04の正規化・バイト数上限も適用する。HTML として解釈しない。入力途中の日本語変換を確定操作と取り違えない。

| 値 | ラベル |
| --- | --- |
| `family` | 家族 |
| `health` | 健康 |
| `study` | 学び・合格 |
| `work` | 仕事 |
| `love` | 恋愛・ご縁 |
| `challenge` | 挑戦 |
| `other` | その他 |

#### 5.3 公開範囲の説明

| 設定 | 説明文 | 公開される面 |
| --- | --- | --- |
| `visibility=public` | 「みんなの地図や一覧に表示する」 | 地図、一覧、個別URL |
| `visibility=unlisted` | 「リンクを知っている人に見せる」 | 個別URL。地図には匿名の占有表示のみ |
| `message_visibility=public` | 「願いの本文も見せる」 | 掲載範囲内のページ・カード画像 |
| `message_visibility=owner_only` | 「願いの本文は自分だけが見る」 | 本文は本人画面のみ。共有面は定型の表面 |

初期値は `visibility=public`、`message_visibility=public`。確定前の確認画面に現在の設定を必ず表示する。

`unlisted` を「非公開」や「自分だけ」と呼ばない。リンクを受け取った人が他者に渡せることを短く説明する。

表示名は任意で、公開用の情報であることを入力欄の近くで伝える。本文を自分だけにしても表示名まで隠れる、と誤解させない。

表示名が未入力なら、UIでは「ななしさん」と表示する。本人の認証情報からメールアドレスや本名を補完しない。

#### 5.4 下書きと確定

- 確定前の入力は現在のタブ内で保持する。必要なら `sessionStorage` を使うが、分析ログや URL には入れない。
- 投稿失敗・認証再試行・枠の取り合いで文面を消さない。
- 投稿成功後は該当下書きを消す。手動で「下書きを破棄」もできるようにする。
- 同じUIDの認証再試行では下書きを保つ。明示的なログアウト・別ユーザーへの切替では前利用者の下書きと本人限定本文を消し、次の利用者へ引き継がない。
- 保存中はボタンを無効化する。同じ操作の再試行には同一の冪等キーを使用する。
- サーバーから成功が返る前に、投稿数や地図上の絵馬を確定済みとして扱わない。
- 有効な絵馬をすでに持つ人には「この年には、すでに絵馬を掛けています」「自分の絵馬を見る」を表示する。

一枚制限の判定単位は `Auth UID × world` の `active` / `hidden` の合計。ゲストが別端末を使った場合に、同一人物だと特定できることは保証しない。画面や利用説明で「全端末を通じて本人を識別する」と案内しない。

### 6. 保存直後の画面

- 見出し：「願いを掛けました」
- 保存した絵馬と、対象年・表示番号を表示する。
- 主操作：「近くに友達を招く」「共有する」
- 補助操作：「画像を保存」「自分の絵馬を見る」
- メール連携は任意として案内する。連携をしなくても投稿・共有は完了できる。
- 案内文例：「この端末から編集できます。別の端末でも使う場合は、メールで引き継ぎを設定できます。」
- ゲスト利用時は、ブラウザのデータ削除等で編集できなくなる場合を案内する。
- 掛ける演出は短く、`prefers-reduced-motion` の指定時は静止状態で完了を示す。
- メール連携や課金への案内で、完了した絵馬を覆う強制モーダルを開かない。

### 7. 詳細画面と本人操作

#### 7.1 公開詳細

- 絵馬、公開を許された本文・表示名、年、表示番号、カテゴリーを表示する。
- 「この絵馬の近くを見る」「近くに掛ける」「共有する」「通報」を用意する。
- 本文を自分だけにした絵馬は「ひみつの願い」と表示する。文字数・原文の一部・カテゴリーから生成した要約を本文の代わりに出さない。
- 掲載範囲や本文の公開設定を変更した場合、リンク先と共有画像へ同じルールを適用する。
- 投稿の `owner_id`、メールアドレス、認証・編集用の情報は公開用 HTML/JSON に出さない。

#### 7.2 本人編集

- 本人画面では、自分の非公開本文と現在の設定を取得できる。
- 所有者であることをサーバー側で検証する。画面上のボタンを隠すだけでは済ませない。
- P0 で編集できるのは願い、表示名、カテゴリー、掲載範囲、本文の公開設定。位置・年・所有者は変更できない。
- 保存時に更新競合があれば上書きを中止し、現在の保存内容を確認して再編集できるようにする。
- 本人画面と認証を含むレスポンスは `no-store`。非公開本文を公開ページの SSR/RSC データへ混ぜない。
- 年の世界がアーカイブ済みなら、願いの通常編集・新規作成・新しいグループへの参加は停止する。削除と公開範囲を狭める操作は続けられる。
- アーカイブ後に可能な公開設定変更は `public → unlisted` と、本文の `public → owner_only`。逆方向の変更は受け付けない。
- P0 では公開詳細、地図チャンク、一覧、個別画像も `Cache-Control: no-store`。本文を含まない概要統計だけは最大30秒の遅れを許容する。

#### 7.3 削除

- 確認文：「この絵馬を削除しますか。元に戻すことはできません。」
- 削除後は地図・一覧・新しく生成する共有画像に本文を出さない。
- 枠は空きに戻る。以前の作品URLを次の利用者へ付け替えない。
- 共有先のSNSや他人が保存した画像まで回収できるとは案内しない。
- 削除した本人には完了を通知し、同じ年の世界へ戻る導線を出す。再投稿は通常の投稿制限を適用する。

### 8. メール連携と復元

- `/me` と投稿完了画面から、任意のメール連携へ進める。
- メールアドレス、認証コード、成功・期限切れ・再送の状態を用意する。
- 確認が終わる前に「引き継ぎ設定済み」と表示しない。
- 既存のアカウントとの競合時は、二つの所有者を自動で合成しない。`04_DATA_AUTH_API.md` の復元方針に沿って案内する。
- 異なる端末で復元した場合に、対象年の自分の絵馬へ戻れること。
- 復帰メールの送信では、登録の有無で文言を変えず「入力内容と受信メールを確認してください」のような共通文言にする。現在のゲストへのメール連携で競合した場合は04の方針で案内し、所有者を自動で切り替えない。
- ログアウト時は本人画面を閉じ、ブラウザ内の非公開本文を消す。公開作品へのリンクは編集権限の代わりにしない。

### 9. 代表的な状態とエラー文言

| 状態 | 表示・操作 |
| --- | --- |
| 初回読み込み | 地図領域のローディング。操作ボタンを多重送信できない状態にする |
| 枠の競合 `409` | 「この場所には、先に絵馬が掛けられました。近くの空いている場所を選んでください。」文面は保持 |
| すでに一枚ある | 「この年には、すでに絵馬を掛けています。」自分の作品へ案内 |
| 認証期限切れ | 「編集できる状態を確認しています。」復元・再試行へ案内 |
| 入力不備 | 該当項目の近くに具体的な修正点を出し、最初の不備にフォーカス |
| 投稿制限 | 「少し時間をおいて、もう一度お試しください。」サーバーの再試行時刻に従う |
| 通信断 | 「送信結果を確認できませんでした。」同じ冪等キーで結果確認・再試行 |
| 世界が受付前 | 公開予定の案内と閲覧。新規確定は不可 |
| 世界がアーカイブ済み | 「この年の絵馬は、いまは眺めることができます。」新しい年への導線 |
| 削除済み・存在しない作品 | 原文を出さず、世界へのリンクを表示 |
| 運営による非表示 | 一般には内容を出さない。本人には状態と問い合わせ導線を表示 |

通報は理由を選んで送信できる。通報者が他人の作品を即座に削除できる機能にはしない。送信後は「通報を受け付けました」と表示し、対応結果の確約はしない。

### 10. アクセシビリティと受入条件

- UX-01：幅 360px、390px、768px、1280px で、作成から共有まで横方向のはみ出しなく完了できる。
- UX-02：タッチ、マウス、キーボードで主要操作に到達できる。地図操作が困難でも一覧から読む・書く・招待できる。
- UX-03：モーダルはフォーカスを内部に保持し、閉じると元の操作へ戻す。入力確定中の Enter を送信に使わない。
- UX-04：項目ラベル、エラー、操作名を読み上げで判別できる。色だけで空き・選択・エラーを表さない。
- UX-05：公開範囲の4通りをプレビューで確認でき、共有カード・リンク先・地図に矛盾がない。
- UX-06：枠競合、通信断、認証再試行が起きても入力内容が残り、重複作品を作らない。
- UX-07：一枚制限に達した人は、既存の自分の絵馬へ戻れる。削除や支払いを誘導して回避させない。
- UX-08：公開詳細のソース、ネットワーク、OG画像、読み上げ文字列に `owner_only` の本文が出ない。
- UX-09：削除・非表示になった作品から、新しい利用者の作品や秘密の編集情報へ遷移しない。
- UX-10：P0 の公開画面に、未実装の決済・描画・3D機能や架空の投稿数が表示されない。
- UX-11：本文と補助文字のコントラスト比を原則4.5:1以上で確認し、操作中・選択中・エラーを色だけで区別しない。
- UX-12：アーカイブ済み世界では、公開範囲の拡大・通常編集・参加をUIとAPIの両方で拒否し、削除・範囲縮小を利用できる。

## Part 3　100万枠の世界と配置

このパートは、絵馬を掛ける場所の座標、地図の表示、探索、友達の近くへの配置を定義する。API・DBの名前と権限の正本は [Part 4](#part-04)、画面構成は [Part 2](#part-02) とする。

### 1. P0の世界

- 1つのworldは **1,000列 × 1,000行 = 1,000,000枠**。年ごとに独立したworldを用意する。
- 初期のworld slugは `2027`。年度は表示用の文字列として扱い、コード全体に固定値を散らさない。
- 1枠に、状態が `active` または `hidden` の絵馬を最大1枚だけ置ける。
- 1つの認証UIDが同一world内に持てる `active` / `hidden` の絵馬は合わせて1枚。「1人1枚」はこの制約を意味し、異なる端末・アカウントの同じ人を厳密に識別する仕様にはしない。
- P0は2D。Canvas 2Dに絵馬の形・模様を描画する。木の質感はSVG等の軽量な素材で表現する。
- 空き枠を100万件DBへ投入しない。空きは座標範囲と占有データから判断する。
- 100万個のDOM要素、100万枚分の画像、絵馬の全件取得を初期表示に使わない。
- 地図・一覧の閲覧だけで匿名アカウントを作成しない。

### 2. 座標と表示番号

| 項目 | 定義 |
|---|---|
| `x` | 左から右へ増える列番号。整数 `0..999` |
| `y` | 上から下へ増える行番号。整数 `0..999` |
| 表示番号 | `slotNumber = y * 1000 + x + 1`。`1..1000000` |
| 逆変換 | `x = (slotNumber - 1) % 1000`、`y = floor((slotNumber - 1) / 1000)` |
| 絵馬の公開ID | 推測しにくいUUID。位置番号とは別に保持する |
| 個別URL | `/w/{worldSlug}/e/{publicId}` |
| 地図URL | `/w/{worldSlug}` |

境界例：`(0,0) → 1`、`(999,0) → 1000`、`(0,1) → 1001`、`(999,999) → 1000000`。

番号は「場所の番号」、公開IDは「作品のID」。削除後に同じ場所へ別の人が掛けても、過去の個別URLがその別の絵馬へ転送されてはならない。

#### 入力の扱い

- 座標・表示番号はサーバーでも範囲と整数性を検証する。
- 範囲外の値を端の座標へ自動補正して投稿しない。入力エラーにする。
- 地図の外側をタップしても枠の選択にしない。
- UIでは通常は表示番号を使い、開発用の座標を主な説明にしない。

### 3. カメラと操作

#### カメラの状態

カメラは `centerX`、`centerY`、`cellPx` を持つ。`centerX/Y` は枠単位の実数、`cellPx` は1枠の幅を表すCSSピクセル数とする。枠の中心は `(x + 0.5, y + 0.5)`。

初期値の目安は `cellPx = 64`、上限は128、下限は0.25。通常の地図領域の高さを最低320 CSS px確保する。極端に小さい表示領域では、全体表示に必要な縮尺を下限として追加許可する。

```text
worldX = (pointerX - viewportWidth / 2) / cellPx + centerX
worldY = (pointerY - viewportHeight / 2) / cellPx + centerY
selectedX = floor(worldX)
selectedY = floor(worldY)
```

Canvasの描画解像度とCSSピクセルは分ける。devicePixelRatioを考慮するが、描画用の倍率は初期値として最大2に制限する。ヒット判定にはCSSピクセルを使う。

#### ポインター操作

| 操作 | 動作 |
|---|---|
| 空き枠をタップ | 番号を表示し「ここに掛ける」を選べる |
| 公開絵馬をタップ | 詳細を開く。戻ると元のカメラ位置へ戻る |
| 非公開扱いの占有枠をタップ | 「この場所には絵馬が掛かっています」。本文・公開IDを取得しない |
| ドラッグ | 地図を移動。移動中に新規作成画面を誤って開かない |
| ピンチ・ズームボタン | 中心点を維持して拡大・縮小 |
| 集計表示の領域をタップ | その付近へ拡大。集計図形から直接空き枠を確保しない |
| 「全体を見る」 | world全体が見える位置と縮尺へ移動 |
| 「自分の絵馬」 | 所有する絵馬へ移動。未作成なら作成入口を表示 |

タップとドラッグの判定閾値は初期値6 CSS px。ジェスチャー処理は地図領域の中に限定し、ページ全体のスクロールやフォーム操作を奪わない。`prefers-reduced-motion` の場合は移動・拡大のアニメーションを省略する。

#### キーボード・代替表示

- 地図にフォーカスがあるときだけ矢印キーで選択枠を移動する。Shift併用は10枠。
- `+` / `-` で拡大縮小、Enterで選択枠に対する操作、Escapeで選択・ダイアログを閉じる。
- 入力欄へフォーカスしている間は地図のキー操作を実行しない。
- 選択した番号と利用可能な操作を、Canvas外のHTMLで表示する。
- 地図には「一覧で見る」入口を常設する。Canvasを使えなくても公開絵馬を読み、自分の絵馬を作成できる。
- 読み込み状態や番号の変化をすべて逐次読み上げない。選択確定と操作結果だけを控えめに通知する。

### 4. 表示の粗さを切り替える

次の値は初期の調整値であり、実機の確認結果に応じて変更してよい。100万件を描かない、非公開情報を公開描画に使わない、という条件は変えない。

| 縮尺の目安 | 表示 | 取得するデータ |
|---|---|---|
| `cellPx < 4` | 密度・色面。個々の絵馬を描かない | 100×100枠または20×20枠ごとの集計 |
| `4 <= cellPx < 24` | 集計を主体に、領域を選んで拡大する表示 | 集計。必要に応じた占有形状のみ |
| `24 <= cellPx < 80` | 個別の絵馬の形・デザイン。本文は描画しない | 可視範囲付近のチャンクの公開DTO |
| `80 <= cellPx` | 絵馬の形と、公開が許可された本文 | 同じ公開DTOの本文を可視範囲で描画 |

#### 集計表示

- 100×100枠の集計は全体で100領域、20×20枠の集計は全体で2,500領域になる。後者はDBチャンクの集計を再利用する。
- `GET /api/v1/worlds/{worldSlug}/overview?cellSize=20|100` で取得する。20×20集計が画面上で密になる場合は100×100集計へ戻す。
- 1回の集計応答は最大2,500領域。本文・名前・公開IDを含めず、100万枚の本文取得とは分ける。
- 密度の説明は「使用中の場所」とする。本文のカテゴリ集計や願いの内容分析はP0に含めない。
- サイトの「掛かっている絵馬の数」は `activeCount`。`active` の実数で、unlistedを含む。サンプル、`hidden`、`deleted` を足さない。
- 空き判定の `occupiedCount` にはhiddenを含める。発見可能な作品数 `listedCount` はactive/publicだけ。3つの数を混同しない。

#### 近景のチャンク

- 1チャンクは20×20枠。`chunkX = floor(x/20)`、`chunkY = floor(y/20)`。それぞれ `0..49`。
- 1回のAPI要求は `/api/v1/worlds/{worldSlug}/chunks?cx={chunkX}&cy={chunkY}` で1チャンクだけ取得する。
- 可視範囲と最大1チャンク分の先読みを要求する。先読みより表示中の領域を優先する。
- 1視点で取得する近景データは最大16チャンク・6,400占有枠を上限とする。
- 同時要求は初期値として4本以下にし、広い画面で上限を超える場合は集計表示へ戻す。
- 通常の1応答は非圧縮JSONで512 KiB以下を目標とする。保護上限は初期値4 MiBとし、最大400件・Part 4の各文字列バイト上限・固定DTOで制限する。異常な超過はエラーとし、粗い表示と再試行を案内する。
- P0は本文の有無で別APIを設けず、公開が許可された本文とニックネームを固定のPublicEmaで取得する。縮小時は本文を描画しない。owner_onlyの本文は縮尺に関係なくnull。
- チャンクの部分応答を返さない。欠けたレコードを空き枠と誤認させない。配信量が大きい場合は同時取得・先読みを減らし、必要なら集計表示へ戻す。
- 未取得の範囲を「空き」と表示しない。読み込み中または未確認とし、取得後に空き判定を表示する。
- API側にも上限を設ける。クライアントからworld全体を近景の応答として要求できない。

### 5. 公開描画用データの範囲

| 絵馬の状態 | 地図の占有 | 地図で公開できる情報 | 個別URL |
|---|---|---|---|
| `active` / `public` / 本文公開 | 使用中 | 公開ID・デザイン・許可された本文プレビュー・表示名 | 公開表示 |
| `active` / `public` / `owner_only` | 使用中 | 公開ID・デザイン・公開の表示名。本文なし | 本文を表示しない公開ページ |
| `active` / `unlisted` | 使用中 | 共通の占有プレースホルダーのみ | URLを知る人は公開設定の範囲で閲覧できる |
| `hidden` | 使用不可 | 共通の占有プレースホルダーのみ | 匿名アクセスは404相当 |
| `deleted` | 空き | なし | 旧作品を表示しない。他人の作品へ転送しない |

`unlisted` の公開ID、名前、本文、カテゴリ、固有デザインは地図の応答に含めない。`owner_only` 本文は、ブラウザーへ渡してから隠す実装を禁止する。

地図は所有者が閲覧している場合も公開用DTOを基本に使う。自分の非公開本文が必要な画面だけ、所有者専用の取得経路を使う。その結果を公開地図のキャッシュへ混ぜない。

### 6. 最初に見せる場所

表示位置の優先順位は次のとおり。

1. 開いた個別URLや有効な招待リンクが指定する場所。
2. 地図URLに明示された有効な位置。
3. その画面へ戻る直前のカメラ位置。
4. 「自分の絵馬」を選んだ場合は自分の位置。
5. 初回の通常訪問では、公開絵馬が集まっていて近くに空きもあるエリア。
6. 公開絵馬がないworldでは中央付近 `(500,500)`。

通常訪問の初期エリアは集計から選び、全絵馬を読み込んで計算しない。密度が高い場所へ偏りすぎないよう候補を数か所持つ。初期エリアの選定から `unlisted` の公開IDや所有者を推定できる情報を返さない。

位置に連動した背景は決定的に生成してよい。装飾用の木や道は、どこが実際の投稿枠かを分かりにくくしない。サンプル絵馬は本番の枚数や実際の投稿として混ぜない。

#### 地図の場所共有

「いま見ている場所を共有」は `/w/{worldSlug}?x={x}&y={y}&z={cellPx}` を生成する。x/yは中心に最も近い範囲内の枠の整数座標、zは1枠あたりのCSS pxで、小数2桁までとする。受け取り時は `(x+0.5,y+0.5)` を中心にする。z省略時は64。不正・非有限の値や範囲外の座標は無視して通常入口へ戻し、読み取り用のzは許容縮尺へ収める。投稿APIの座標を自動補正することとは区別する。

個別詳細の「地図で見る」はその作品のx/yとz=80を使う。場所URLは作品の所有権や限定URLへのアクセス権を与えず、通常の公開地図だけを表示する。unlisted作品の識別子を位置URLへ付けない。パン中に履歴を大量追加せず、操作終了時の `replaceState` または明示的な共有時にURLを更新する。

### 7. 探索

P0は次に限定する。

- 表示番号から、その場所へ移動する。
- 新しく公開された絵馬を一覧で読む。1ページ既定24件、API最大50件のカーソルページング。
- 公開一覧をカテゴリで絞る。`family / health / study / work / love / challenge / other` のみ許可し、unlistedを検索対象にしない。
- 公開絵馬をランダムに1枚見る。対象は `active + public` のみ。
- 自分の絵馬へ戻る。
- 招待された絵馬の近くを見る。

全文検索、ニックネーム検索、人気ランキングは後続にする。ランダム表示も、毎回全件をソートする実装を前提にしない。抽選用の候補・インデックス等はPart 4のDB設計で決める。

一覧で絵馬を開いて地図へ移動するときは、その絵馬が分かる縮尺へ移動する。非公開本文の場所には、Part 2の定型文言を表示する。本文から要約を生成して代わりに出さない。

### 8. 枠選択から投稿確定まで

1. 利用者が空き枠を選ぶ。
2. 地図上に「選択中」を表示する。この段階では枠を予約しない。
3. 文面、表示名、カテゴリ、公開設定、デザインを入力する。
4. 公開される状態をプレビューする。
5. 投稿確定時に、認証・worldの受付状態・所有数・枠の空き・内容をサーバーで検証する。
6. DBトランザクションで1枚だけ確定する。
7. 成功した公開IDを受け取ってから、地図に掛かった表示と共有画面へ進む。

ネットワークが遅くても成功アニメーションを先に出さない。確定リクエスト中は同じ操作の連打を防ぎ、再送には同じ冪等キーを使う。

#### 同じ枠を別の人が先に使った場合

- Part 4の `409 SLOT_TAKEN` を表示する。
- 入力済みの文章・公開設定を失わない。
- 近くの空き枠を複数提案し、本人が選び直せるようにする。
- サーバーや画面が無断で遠くの枠へ配置しない。
- 確定済みか不明な通信切断では、同じ冪等キーで結果を確認してから再選択させる。

P0では作成後の場所移動を実装しない。本文の編集と場所の移動を同じ更新処理にしない。削除後の新規作成は通常の作成制限・回数制限の対象とする。

### 9. 友達の近くへの招待

作成入口は `/w/{worldSlug}/new?near={publicId}` を使用する。直接座標で開く場合は `?x={x}&y={y}` を使用できる。両方ある場合は `near` を優先する。無効な `near` から座標指定へ黙って切り替えず、理由を表示して再選択させる。

#### 候補の探し方

- 招待元の座標を中心に、まず3枠、その後8枠、20枠の範囲を探す。範囲は `max(abs(dx), abs(dy)) <= r` の正方形とする。
- `GET /api/v1/worlds/{worldSlug}/nearby?near={publicId}` は距離の近い候補から最大8件返す。距離は `dx*dx + dy*dy`、同距離なら表示番号の昇順とする。
- 範囲外の座標は候補に入れない。境界・角の枠も同じ処理で扱う。
- 候補取得は予約ではない。確定時に再度競合確認する。
- 20枠の範囲内に空きがなければ、別のエリアを探す操作を案内する。自動的に配置しない。
- 招待によって作成上限やアクセス権限は変わらない。

#### 例外

| 状況 | 振る舞い |
|---|---|
| 招待元が `active + public` | 招待元を見せ、近くの空きを案内する |
| 招待元が `unlisted` | 利用者がそのURLを持つ前提で、個別ページと同じ公開設定で表示する。地図の他の閲覧者へIDを公開しない |
| 招待元が `hidden` または `deleted` | 「この絵馬は現在表示できません」。対象worldの通常の作成入口へ戻り、場所を選び直す |
| 別worldのIDを指定 | 不一致として扱う。他の年へ黙って投稿しない |
| 無効なUUID | 入力エラーの説明後、通常の作成入口から再選択できる。URL由来の文字列をHTMLとして表示しない |
| 本人がこのworldに作成済み | 新規投稿へ進めず、自分の絵馬を案内する |
| worldが受付終了 | 閲覧へ案内し、そのworldへの新規投稿を無効にする |

`archived` のworldでは新規作成・本文編集・グループ参加を許可しない。本人による削除、`public → unlisted`、`message_visibility: public → owner_only` の公開範囲縮小は許可する。公開範囲の拡大は許可しない。

### 10. 取得・描画の実装制約

- カメラ移動は `requestAnimationFrame` で描画し、ネットワーク要求は移動後の150〜250msを初期目安にまとめる。
- 同じチャンクへの重複要求をまとめ、移動前の不要な要求を中断する。
- 応答に対応するworld・表示範囲・要求世代を照合し、遅れて届いた結果で新しい表示を上書きしない。
- カメラの高頻度更新でReactの全画面を再描画しない。HUDと地図の描画経路を分ける。
- 絵馬の素材はデザイン別に再利用する。1枚ごとに巨大な画像を持たない。
- 個別・チャンク・一覧・OG/PNG画像の応答はP0では `Cache-Control: no-store`。本文等を持たないoverviewの統計だけ最大30秒の遅延を許す。詳細な設定はPart 4に従う。
- 非公開本文と所有者情報を共有キャッシュへ格納しない。クライアント内の一時データも、削除・非表示・公開範囲変更後や認証ユーザー切替後に保持し続けない。
- スマホの画面外・タブが非表示のときは不要な描画や再取得を止める。
- P0では全worldに対するRealtime購読を行わない。可視範囲の低頻度更新と自分の操作後の再取得で開始する。

### 11. このパートの受入条件

| ID | 確認内容 |
|---|---|
| WORLD-01 | 4つの境界例の番号変換が正しく、範囲外の枠へ作成できない |
| WORLD-02 | 初期表示で全件取得・100万DOM・100万空きレコードの投入が発生しない |
| WORLD-03 | 全体から個別まで拡大でき、集計表示と実際の配置位置が一致する |
| WORLD-04 | 空き・読み込み中・占有を区別でき、未取得範囲へ即確定しない |
| WORLD-05 | 2人が同時に同じ枠へ送信しても成功は1人だけで、もう1人の文面が残る |
| WORLD-06 | 招待元が端・角・削除済み・別world・周辺満員でも説明付きで進める |
| WORLD-07 | unlistedのID・本文・名前とowner_only本文が公開地図の通信応答に含まれない |
| WORLD-08 | 一覧・キーボードからも公開絵馬の閲覧と新規作成へ到達できる |
| WORLD-09 | 詳細から戻ったときにカメラ位置が復元され、別worldの古い応答が混ざらない |
| WORLD-10 | 自分の投稿確定後に更新され、通信失敗を成功として表示しない |

検証条件と計測結果は [Part 7](#part-07) の形式で記録する。

## Part 4 — データ・認証・API仕様

版: v1.0 / 仕様基準日: 2026-10-28 / 対象: P0本公開、末尾にP1・P2の拡張境界

本書をAPIパス、DTO、DB不変条件、認証と権限の正本とする。機能範囲はPart 1、画面はPart 2、地図はPart 3、共有体験はPart 5を参照する。ここで決める数値は本プロダクトの初期設定であり、外部サービスの上限や実測値ではない。

### 1. 採用する構成

- Web/BFF: Next.js App Router + TypeScript。ブラウザからデータ操作を行う窓口は同一オリジンの `/api/v1`。
- 認証: Supabase Auth。匿名セッションとメールOTPを利用する。Supabase SSR公式構成を使用し、依存バージョンとlockfileを固定する。[S1][S2]
- DB: Supabase Postgres。原本と補助テーブルは非公開schema `app_private`。このschemaをSupabase Data APIの公開対象に追加しない。
- BFFはサーバー専用の限定DBロールで接続する。通常APIに `postgres`、テーブル所有者、`BYPASSRLS`、`service_role` を使用しない。
- 接続には対応するトランザクションプールを使用する。DB秘密情報はサーバー環境変数のみ。ブラウザにはAuth用publishable keyとURLだけを渡す。
- UI向け型とサーバー入力バリデーションを共通定義し、OpenAPIまたは同等の型付き契約をリポジトリに残す。SQLから生成した行型をそのまま公開DTOにしない。
- P0では `ENABLE_GROUPS=false`、`ENABLE_FULFILLMENT=false`、`ENABLE_PAYMENTS=false`。サーバー設定を正本とし、UIには真偽値のcapabilitiesだけを返す。未開放機能はAPI側でも拒否する。P2導入後のpayments flagは新規販売を止めるもので、既存注文照合・Webhook・返金・購入権利の表示は止めない。

これは新規実装の推奨構成であり、既存リポジトリの技術構成が異なる場合は同じ不変条件を保って置き換えてよい。サービスの新規契約・本番接続・デプロイは、この仕様書の作成だけでは実行しない。

### 2. 不変条件

| 項目 | 契約 |
|---|---|
| world | 年別。初回slugは `2027`。slugはimmutable・unique |
| サイズ | 幅1,000 × 高さ1,000。`x,y` は整数0〜999 |
| 表示番号 | `slotNumber = y * 1000 + x + 1`。1〜1,000,000 |
| chunk | 20 × 20。`cx=floor(x/20), cy=floor(y/20)`。各0〜49 |
| 作品ID | サーバー生成UUID v4。座標から生成しない。削除後も他作品に再利用しない |
| 正規URL | `/w/{worldSlug}/e/{publicId}`。URLに所有者UID、秘密、本文を入れない |
| 所有数 | 1 UIDにつき1 worldにactiveまたはhiddenの絵馬を1枚まで |
| 配置 | 1 worldの1座標にactiveまたはhiddenを1枚まで。公開後の移動はP0対象外 |
| 下書き | ブラウザ内のみ。場所の選択・下書き保存・近隣候補取得では予約しない |
| 本文 | NFC正規化後、1〜80書記素。plain text。HTML/Markdownとして解釈しない |
| ニックネーム | 任意、NFC正規化後0〜20書記素。空文字はnull |
| 分類 | `family / health / study / work / love / challenge / other` |
| デザイン | P0は `basic_wood` のみ。未知IDや未購入IDはサーバーで拒否 |
| 時刻 | DBは `timestamptz` のUTC。表示と運用スケジュールはAsia/Tokyo |

「1人1枚」は実装上「1 UIDにつき1枚」であり、Cookieを消した人の再匿名登録を厳密に同一人物と判定する保証はしない。IPだけで所有者を識別しない。

入力はサーバーで正規化し、クライアントも同じ処理でプレビューする。改行はLFへ統一し、本文前後の空白を除去。本文は最大4行、nicknameは1行。NUL、不要な制御文字、双方向制御による表示偽装文字を拒否し、絵文字のZWJ・結合文字は保持する。書記素数は `Intl.Segmenter` 相当で数え、`string.length` やDBの文字数だけで代用しない。全リクエストJSONは8KiBまで、本文UTF-8は4KiB、nicknameは1KiBまでの別上限も設ける。URLらしい文字列もリンク化せず通常テキストで表示する。

### 3. 状態と公開範囲

#### 3.1 worldと作品の状態

| 状態 | 許可する操作 |
|---|---|
| world `preview` | 公開済み情報の閲覧、ローカル下書き、本人削除、公開範囲の縮小。新規配置・本文編集は禁止 |
| world `open` | 公開期間内に新規配置、本人編集、削除、公開範囲変更 |
| world `archived` | 閲覧、本人削除、公開範囲の縮小のみ。新規・本文編集・グループ参加は禁止 |
| ema `active` | 指定された公開範囲で表示。本人が編集可能 |
| ema `hidden` | 管理者非表示。座標と本人枠を保持。公開APIでは存在しない扱い、地図はoccupied |
| ema `deleted` | 座標と本人枠を解放。本文・nicknameを消去。復元・ID再利用は禁止 |

新規配置・本文編集は `state='open' AND opens_at <= DB現在時刻 < closes_at` をトランザクション内で判定する。状態切替ジョブの遅延だけで締切後の投稿を許可しない。公開範囲の縮小は `public→unlisted` と `message_visibility: public→owner_only`。archivedでは逆方向の変更やnickname/design/categoryの変更を許可しない。hiddenは本人削除と公開範囲の縮小のみ可能で、本人編集でactiveへ戻せない。

運営の新規受付停止は `posting_enabled=false` で表す。新規配置にはさらに `posting_enabled=true` が必要。削除・公開範囲の縮小・通報・閲覧をこのフラグで止めない。`acceptingPosts` はDB時刻、state、期間、posting_enabledからサーバーで計算する。受付の一時停止だけでworldをarchivedにしない。

#### 3.2 2つの独立した設定

| 設定 | `public` | もう一方の値 |
|---|---|---|
| `visibility` | 地図・一覧・ランダム訪問から発見できる | `unlisted`: 正確なURLを知る人は閲覧可能。公開一覧には出さない |
| `message_visibility` | 願い事本文を訪問者と共有画像に表示する | `owner_only`: 本文を本人APIだけで返す。公開表示は「ひみつの願い」 |

nickname、category、design、座標は直接作品URLで表示する公開項目。本文を非公開にしてもnicknameは非公開にならないことを入力画面で説明する。unlistedは認証付きの非公開機能ではない。

unlisted/hiddenの地図データは `{ kind:'occupied', x, y, slotNumber }` のみ。publicId、nickname、category、design、本文、更新日時を載せない。公開詳細、共有画像、HTML、RSC payload、JSON-LD、OGメタデータ、エラーレスポンス、ログにもowner_only本文を混入させない。

### 4. 認証・本人管理

#### 4.1 閲覧と匿名投稿

1. 閲覧だけの人には匿名ユーザーを作成しない。public APIはCookie不要で利用できる。
2. 作成画面で入力開始時、必要な場合だけ匿名サインインする。二重タップ・複数タブを含め、既存セッションを確認してから開始する。
3. 匿名AuthにもCAPTCHA/不正利用対策を設定する。匿名Authの利用者はDB上の `authenticated` ロールになり得るため、ロール名だけで所有権を判断しない。[S1]
4. 投稿APIはサーバーで検証済みのUIDを所有者にする。入力JSON内の `owner_id`、`ownerId`、`status`、`publicId`、`version` など未定義キーは422で拒否する。
5. 本人管理画面はセッションCookieから本人APIを呼ぶ。localStorage内のIDや「編集URL」だけでは編集できない。

#### 4.2 任意メール登録と復帰

- 投稿後に「この絵馬をあとから管理する」を案内する。登録しなくても公開は完了する。
- **匿名からの登録**: 現在の匿名セッションに `updateUser({email})` でidentityを追加し、メール確認を完了する。同一UIDを保つ。メール確認前を登録完了と表示しない。必要なmanual linking設定は実装時の公式手順に従う。[S1]
- **別端末からの復帰**: 登録済みメールへOTPを送信する。`signInWithOtp` は復帰フローで `shouldCreateUser:false` を指定する。未登録メールでも送信要求のUIは同じ一般的な文言にする。[S3]
- OTPメールはコード入力に対応するテンプレートを設定する。確認はSDKの `verifyOtp` を使用し、メール追加とログインの用途を取り違えない。固定したSDKの公式仕様を確認する。[S4]
- 匿名セッション消失後、メール未登録の作品を公開URLやnicknameだけで本人へ復帰させない。「このブラウザのデータを消すと管理できなくなります」と事前表示する。
- 追加先メールが既存アカウントに属する場合、P0は自動統合しない。`ACCOUNT_LINK_CONFLICT` を表示し、現在の作品を維持する。既存アカウントへ切替する前に未登録作品を管理できなくなる可能性を説明する。
- 所有権の付け替えを任意UIDを受け取るAPIで実装しない。将来の統合は双方のセッション証明と同world重複解消を含む別仕様とする。

#### 4.3 検証とセッション分離

通常の本人APIは `getClaims()` 等でJWTを検証し、UIDを取得する。管理操作、メール登録状態が条件となるグループ作成には `getUser()` 等で最新のユーザー状態も確認する。Cookie内のuser JSONや検証していない `getSession()` 結果だけを権限判定に使わない。[S2]

Auth/本人/APIレスポンスは `Cache-Control: private, no-store`。認証に触れるSSR/RSCも共有キャッシュへ入れない。リクエストごとにSSRクライアントを生成し、別ユーザーへ `Set-Cookie` を転用しない。Cookie更新に伴うレスポンスヘッダーを失わない。セッション保存はSDKの公式方式を使い、独自JWTや編集トークンを追加しない。

全変更APIで許可Origin、同一サイトの要求、JSON Content-Typeを確認する。クロスサイトCookie要求を拒否し、必要なCSRF対策を実装する。Authメール送信・認証試行にも独立した制限を適用する。Authorizationヘッダー、Cookie、OTP、メールアドレスをアクセス解析へ送らない。

### 5. DBモデル

P0は実際の作品行だけを挿入する。100万の空枠や100万の空絵馬を事前作成しない。

| テーブル | 主な列・目的 |
|---|---|
| `worlds` | id UUID PK、slug unique、name、state、posting_enabled boolean default true、width=1000、height=1000、opens_at、closes_at、created_at |
| `emas` | id bigint内部PK、public_id UUID unique、world_id FK、owner_id UUID、x/y、slot_number生成列、wish_text、nickname、category、design_id、visibility、message_visibility、status、version、created_at、updated_at、deleted_at |
| `ema_public_projection` | ema_id PK/FK、public_id、world_id、x/y、slot_number、公開nickname/category/design、visibility、message_visibility、**公開可能な本文だけ**、version、created_at、updated_at |
| `slot_occupancy` | world_id、x/y、ema_id unique FK。PK(world_id,x,y)。active/hiddenだけを保持。本文/UID/nicknameなし |
| `world_chunks` | PK(world_id,cx,cy)、occupied_count、active_count、listed_count、revision、updated_at。各countは0〜400 |
| `idempotency_records` | owner_id、operation、key_hash、request_hash、result_public_id任意、result_version任意、receipt_json、http_status、created_at。receiptは許可されたID/結果/版だけ。本文を複製しない |
| `reports` | id UUID、ema_id、reporter_id、reason、detail任意、state=`open\|resolved\|dismissed`、version、created_at、resolved_at。通報者は非公開 |
| `admin_users` | user_id PK、role=`moderator`、enabled、created_at。管理者のサーバー管理台帳 |
| `moderation_audit` | id、admin_id、ema_id、action、reason_code、before_status、after_status、created_at。本文コピーを保存しない |
| `rate_limit_buckets` | action、subject_hash、window_start、count、expires_at。共有DBまたは同等の耐久ストアで代替可 |

`ema_public_projection` はactiveのみ保持し、owner_onlyの本文列は必ずNULL。unlistedの直接詳細に必要な投影は保存できるが、公開一覧のクエリは `visibility='public'` を必須条件にする。原本と公開投影の同期を非同期ジョブへ丸投げしない。

countは `listed_count <= active_count <= occupied_count <= 400`。activeはunlistedを含みhiddenを除く。occupiedはactiveとhidden、listedはactiveかつpublic。「掛かっている絵馬の数」にはactive_countの合計を使う。

owner_idはAuthのUID。Authユーザーの一括削除を作品へ無条件CASCADEしない。匿名Authの整理ジョブは作品・通報・グループを保有しない休眠アカウントだけを対象にする。アカウント削除を実装する場合は、先に本人作品の削除とセッション失効を行う専用手続きを追加する。

#### 5.1 必須制約・indexの参考SQL

以下はmigration設計の核であり、schema全体・列型・RLS・権限を省略した参考断片である。そのまま「検証済みmigration」として適用しない。

```sql
alter table app_private.emas
  add constraint emas_xy_check
    check (x between 0 and 999 and y between 0 and 999),
  add constraint emas_version_check check (version >= 1);

create unique index emas_live_slot_uq
  on app_private.emas (world_id, y, x)
  where status in ('active', 'hidden');

create unique index emas_live_owner_uq
  on app_private.emas (world_id, owner_id)
  where status in ('active', 'hidden');

create unique index idempotency_owner_operation_key_uq
  on app_private.idempotency_records (owner_id, operation, key_hash);

create index ema_public_feed_idx
  on app_private.ema_public_projection
  (world_id, created_at desc, public_id desc)
  where visibility = 'public';

create index ema_public_category_feed_idx
  on app_private.ema_public_projection
  (world_id, category, created_at desc, public_id desc)
  where visibility = 'public';
```

加えて、public_id unique、world/ema FK、enum/check、deleted時の本文・nickname NULL、active/hidden時の本文必須、slot_number生成列、world期間の前後関係をDBで制約する。座標検索にはoccupancyのPKとprojectionの `(world_id,y,x)`、本人一覧には `(owner_id,world_id)` を設ける。API最大件数に対してEXPLAINで確認し、不要なindexは追加しない。

### 6. DBアクセス境界とRLS

#### 6.1 サーバーからのアクセス

通常DBロールは `emanowa_app` を例とし、`NOSUPERUSER NOBYPASSRLS`、原本の非所有者とする。migration専用ロールと分離する。ブラウザ、公開Supabaseロール `anon/authenticated`、`PUBLIC` へ内部schemaの利用権限・内部関数のEXECUTEを付与しない。[S5]

1. BFFでセッションを検証し、必要な権限を判断する。
2. DB接続を1つ取得し、BEGINする。
3. パラメーター付き `set_config('app.actor_id', verifiedUid, true)` を同じトランザクション内で設定する。公開APIは空値。
4. 内部の `current_actor_id()` は空値ならNULL、正しいUUIDならその値を返す。これはBFFが設定する信頼境界であり、ブラウザ入力をコピーしてはいけない。
5. invoker関数または同一接続のパラメーター付きSQLで処理し、COMMIT/ROLLBACKする。接続返却後にactorが残らないことをテストする。

Supabase Data APIを経由しない直接Postgres接続では `auth.uid()` が自動で埋まると仮定しない。上記のアプリ用コンテキストを利用する。ユーザー指定のSQL、任意schema、任意sort列を実行しない。

#### 6.2 権限行列

| データ | 公開API | 本人API | 管理API |
|---|---|---|---|
| world / 内容なし統計 | 許可されたDTOのみ | 同左 | 設定変更は運用のみ |
| ema原本 | 参照不可 | `owner_id=current_actor_id()` の行のみ | 監査対象のモデレーション処理のみ |
| 公開投影 | public一覧 / UUID一致の直接詳細 | 公開投影を流用せず本人DTO | owner_only本文を管理画面へ表示しない |
| occupancy | 座標の占有情報のみ | 配置transactionの必要範囲 | hidden/deleteに連動 |
| reports | 自分の通報作成のみ | 他人の通報者情報は不可 | 管理者のみ一覧・解決 |
| admin_users / audit | 不可 | 不可 | 有効な管理者のみ、監査保存 |
| idempotency | 不可 | 自分のoperation/keyのみ | 障害調査は必要最小限 |

原本はRLSを有効にし、SELECT/INSERT/UPDATEの所有権条件を設定する。UPDATEはSELECTポリシーとUSING/WITH CHECKの両方が必要。owner_id/world_id/public_id/x/yを一般編集で変更できない列権限・関数境界を設ける。[S5]

公開projectionの列には秘密情報を入れない。通常一覧とUUIDによる詳細を別query関数に分ける。さらにRLSでpublicのみ許可し、直接詳細の場合だけBFFがtransaction-localに指定したlookup UUID一致を許可する。クエリ引数だけで任意ユーザー・任意非公開一覧を解禁しない。occupancyの内部ema_idはDTOへ投影しない。

配置・更新は原則 `SECURITY INVOKER`。補助テーブルにも実際の処理に必要なRLSとgrantだけを付ける。特権関数が不可避なら内部schemaに限定し、固定search_path、テーブルの完全修飾、PUBLIC/anon/authenticatedからEXECUTE revoke、専用ロールへの最小grant、本文中の検証済みactor UID確認を必須にする。管理関数はさらにadmin_usersの現在値を確認する。所有者権限のviewやdefinerでRLSを無自覚に迂回しない。[S5]

管理者判定はサーバー管理のadmin_usersを毎回確認する。利用者が編集できる `user_metadata`、nickname、メールの文字列一致だけから管理者権限を付与しない。管理者は確認済みメールとMFAを必須とし、通常投稿用DB接続へ管理権限を持たせない。

管理APIでは検証済みJWTの認証保証レベルがMFA完了相当であることも確認する。管理画面の表示可否とAPIの権限判定を分け、API側を省略しない。

### 7. DTOの正本

JSONはcamelCase、DBはsnake_case。全日時はUTCのISO 8601文字列。内部ID、owner UID、メール、IP、管理理由の自由記述は公開DTOに含めない。publicIdはUUID文字列。

```ts
type Category = 'family'|'health'|'study'|'work'|'love'|'challenge'|'other';
type Visibility = 'public'|'unlisted';
type MessageVisibility = 'public'|'owner_only';
type PublicEma = {
  publicId: string; worldSlug: string;
  x: number; y: number; slotNumber: number;
  nickname: string|null; category: Category; designId: 'basic_wood';
  visibility: Visibility; messageVisibility: MessageVisibility;
  messageText: string|null; // owner_onlyは必ずnull
  version: number; createdAt: string; updatedAt: string;
};
type ChunkCell =
  | { kind:'public'; ema: PublicEma }
  | { kind:'occupied'; x:number; y:number; slotNumber:number };
type ChunkResponse = {
  worldSlug:string; cx:number; cy:number; revision:number;
  cells:ChunkCell[]; // 0〜400件。存在しない座標はempty
};
type OwnerEma = {
  publicId:string; worldSlug:string; x:number; y:number; slotNumber:number;
  nickname:string|null; category:Category; designId:'basic_wood';
  visibility:Visibility; messageVisibility:MessageVisibility;
  wishText:string; status:'active'|'hidden'; version:number;
  createdAt:string; updatedAt:string;
  capabilities:{editContent:boolean;
    visibilityMode:'all'|'restrict_only'|'none';delete:boolean};
};
type MutationReceipt = {
  publicId:string; worldSlug:string; version:number;
  result:'created'|'updated'|'deleted'; canonicalUrl:string;
};
type ApiError = {
  error:{code:string;message:string;requestId:string;
    fieldErrors?:Record<string,string>;retryAfterSeconds?:number};
};
```

公開本文nullの表示文言はUIが生成する。`messageText` に本当の秘密本文を渡してCSSで隠す実装は禁止。OwnerEmaは独立schemaとし、PublicEmaの型キャストだけで出力しない。mutationはreceiptだけを返し、本人画面は必要に応じてOwnerEmaを再取得する。

### 8. P0 API一覧

`{slug}` はworldSlug、`{id}` はpublicId。成功レスポンスは下表の形を固定する。JSON成功時は `Content-Type: application/json`、画像のみPNG。全変更APIは同一オリジン限定。`owner` は検証済み匿名/登録ユーザー、`admin` は追加の管理者認証を表す。

| Method / path | 認証 | 入出力・制約 |
|---|---|---|
| GET `/worlds/{slug}` | 不要 | `{world:{slug,name,state,width,height,opensAt,closesAt,acceptingPosts},serverTime,stats:{occupiedCount,activeCount,listedCount,asOf},capabilities:{groups,fulfillment,payments}}`。serverTimeはDB現在時刻、no-store |
| GET `/worlds/{slug}/overview?cellSize=20` | 不要 | `{cellSize,cells:[{x,y,occupiedCount,activeCount,listedCount}],asOf}`。cellSizeは20（既定）または100。各cell左上座標、最大2,500または100集計。本文/IDなし |
| GET `/worlds/{slug}/chunks?cx=&cy=` | 不要 | `ChunkResponse`。整数0〜49。1要求につき1chunk |
| GET `/worlds/{slug}/emas?limit=&cursor=&category=` | 不要 | `{items:PublicEma[],nextCursor:string\|null}`。public/activeのみ。limit既定24、最大50 |
| GET `/worlds/{slug}/emas/random?category=` | 不要 | `{item:PublicEma\|null}`。public/activeのみ。大量OFFSETや全件ブラウザ取得は禁止 |
| GET `/worlds/{slug}/emas/{id}` | 不要 | `{ema:PublicEma}`。unlistedは正しいIDなら可。hidden/deleted/別worldは404 |
| GET `/worlds/{slug}/nearby?near={id}` | 不要 | `{origin:{x,y},candidates:[{x,y,slotNumber}],searchedRadius}`。最大8候補。searchedRadiusは3/8/20 |
| GET `/worlds/{slug}/nearby?x=&y=` | 不要 | 同上。nearとx/yの同時指定は400。座標は0〜999 |
| POST `/worlds/{slug}/emas` | owner | `CreateEmaInput`。`Idempotency-Key`必須。201 `{receipt:MutationReceipt}` |
| GET `/me/emas?world={slug}` | owner | `{ema:OwnerEma\|null}`。hiddenも本人へ返す。deletedはnull |
| GET `/me/worlds?limit=&cursor=` | owner | `{items:OwnerWorldSummary[],nextCursor}`。自分のactive/hidden絵馬がある年を新しい順に返す。limit既定12、最大50 |
| PATCH `/me/emas/{id}` | owner | `UpdateEmaInput`。200 `{receipt}`。所有権とversionを検証 |
| DELETE `/me/emas/{id}` | owner | JSON `{expectedVersion}`。200 `{receipt}`。本文抹消・枠解放 |
| POST `/worlds/{slug}/emas/{id}/reports` | owner | `{reason,detail?}`。201 `{reportId,accepted:true}`。本人が未登録でも通報可。同一UIDの同作品へのopen通報があれば200で既存reportId |

| POST `/admin/emas/{id}/moderation` | admin | `{action:'hide'\|'restore'\|'delete',reasonCode,expectedVersion}`。監査記録必須 |

表中のパスはすべて `/api/v1` が先頭。UIの正規作品URLは `/w/{slug}/e/{id}`。画像routeをフレームワークのOG routeへ委譲しても、このAPI契約は維持する。

```ts
type CreateEmaInput = {
  x:number; y:number; wishText:string; nickname?:string|null;
  category:Category; designId:'basic_wood';
  visibility:Visibility; messageVisibility:MessageVisibility;
};
type UpdateEmaInput = {
  expectedVersion:number;
  wishText?:string; nickname?:string|null; category?:Category;
  designId?:'basic_wood'; visibility?:Visibility;
  messageVisibility?:MessageVisibility;
};
type OwnerWorldSummary = {
  worldSlug:string; worldName:string; worldState:'preview'|'open'|'archived';
  ema:{publicId:string;slotNumber:number;status:'active'|'hidden';
    designId:string;visibility:Visibility;messageVisibility:MessageVisibility;
    version:number;updatedAt:string};
};
```

PATCHは指定フィールドだけを更新する。省略とnullを区別し、nicknameだけnullで消去可能。空PATCH、未知キー、座標/owner/statusの変更を422にする。変更値が同一でも成功時にversionを1増加させる。DELETE/PATCH/通報/管理変更にもIdempotency-Keyを必須にする。

通報reasonと管理reasonCodeは `spam / harassment / personal_information / sexual_content / illegal_content / other` の列挙値。通報detailは任意200書記素、UTF-8 2KiB以内のplain text。`(reporter_id,ema_id) WHERE state='open'` をuniqueにし、同じ人の連投でキューを増やさない。通報は非表示の投票ではなく、件数だけで自動hiddenにしない。

日本語ラベルは順に「宣伝・スパム」「嫌がらせ」「個人情報」「性的な内容」「違法行為に関する内容」「その他」。`/me` の年別一覧は `/me/worlds` を使い、年を開いたときだけ `/me/emas?world=` で本人の本文を取得する。年別一覧のcursorも検証し、他人のUIDをqueryに受け付けない。

#### 8.1 認証用BFF route

| POST path | 契約 |
|---|---|
| `/api/v1/auth/anonymous` | `{captchaToken}`。有効な既存セッションがあれば再利用。新規時のみ匿名Authを作成。Cookieを設定し `{authenticated:true,isAnonymous:boolean}`。既存登録済みユーザーを匿名へ戻さない |

#### 8.2 ページング・近隣検索

一覧は `(created_at DESC, public_id DESC)` のkeyset pagination。cursorにworld/category/orderを含め署名または厳密検証し、不正なcursorは400。ページ間の新規投稿により表示が変わることは許容するが、クライアントはpublicIdで重複除去する。

nearbyは参照作品のworldとactive状態を確認する。unlistedは直接IDを知る人の招待に使用可。hidden/deletedは404。原点からChebyshev距離3、8、20の順に探索を広げ、距離の二乗 `dx*dx+dy*dy`、slotNumberの順で最大8件。8件得られた段階か半径20で打ち切り、実際の探索半径を返す。最大41×41の範囲に限定し、見つからなければ空配列を返して別の場所へ案内する。候補は予約ではなく、確定時に再検証する。

UIの作成URLにnearと座標が混在した場合はnearを優先し、APIにはどちらか一方だけ渡す。近隣リンクから他人の公開範囲や所有権は変化しない。

### 9. トランザクションと競合

#### 9.1 新規配置

1. リクエストサイズ、Origin、認証、入力、制限を検証する。入力を正規化してrequest_hashを作る。
2. BEGIN後、検証済みactorをtransaction-localに設定する。冪等性キー単位のロックまたはunique行で直列化する。
3. 既存の成功記録があればhashを比較し、同じなら保存したreceiptを返す。違えば409。
4. world状態・投稿期間・posting_enabledと所有数をDBで再検証する。所有数の最終保証はpartial unique indexとする。
5. emas、occupancy、公開projectionを挿入する。public_idはここで生成する。座標/所有数のunique違反を対応する409へ変換する。
6. 対象chunkのcount/revisionと、必要な耐久制限・冪等性成功記録を更新する。
7. すべてを同一transactionでCOMMITしてから201を返す。一部だけ成功したレスポンスを返さない。

公開projectionへはmessage_visibilityがpublicの場合だけ本文をコピーする。クォータ、原本、占有、投影、chunk count、成功記録の更新を別HTTPリクエストへ分割しない。率制限を外部ストアで先に消費する場合は、失敗時に試行回数が残ることを許容し、所有数の正確性をそのストアへ依存させない。

競合時、選択位置を勝手に変更して投稿しない。UIは本文/設定を保持し、近隣候補を再取得する。同じ人の同時投稿が別座標に到達した場合も1枚のみ成功させる。

#### 9.2 編集・削除・管理非表示

- 行をロックして本人/管理者権限、state、`expectedVersion === version` を確認する。不一致は409 `VERSION_CONFLICT`。新しい本文で上書きしない。
- 成功時にversionを1増加し、投影とchunk revision/countを同一transactionで更新する。
- hidden化: projectionを削除、occupancyは維持、active_countを減らし、元がpublicならlisted_countも減らす。本人の1枚枠は保持する。
- restore: activeへ戻し、現在の公開設定からprojectionを作り直す。deletedからrestoreは禁止。
- delete: 原本をdeletedへ変更しwish_text/nicknameをNULL、projectionとoccupancyを削除、chunk countを減らす。監査・冪等性に本文を残さない。
- countの差分は変更前後の状態から算出する。hiddenのdeleteでactiveを二重に減らさず、public→unlistedではlistedだけを減らす。
- 削除後の公開URLは404。新しい作品が同じ座標に入っても古いIDから転送しない。本人の同じdelete再送は同じreceiptを返す。
- 画像生成は公開投影を読み、そのversionの画像を生成後、返却直前に現在version/公開状態を再確認する。途中で縮小/削除された場合は破棄して再取得または404にする。

#### 9.3 冪等性の詳細

`Idempotency-Key` はクライアントが操作開始時に生成するUUID v4。送信が不明な場合の再試行は同じkeyと同じbodyを使う。本文や座標を変えてやり直す場合は新しいkeyにする。

unique範囲は `(owner_id, operation, key_hash)`。operationにはHTTP操作と対象worldまたはpublicIdを含める。正規化したbodyと対象pathのcanonical JSONをSHA-256等でhash化する。同じkeyの同時要求は1つだけが実行され、他方は完了を待つか503で再試行を案内する。

成功receiptは不変で本文を含まない。作成後に削除しても同じcreate再送で作品を復活させない。再送receiptのversionはその操作が成功した時点の値であり、現在状態は本人GETで確認する。失敗したtransactionの成功記録は残さない。成功keyの最低限の記録はworldと作品tombstoneの存続中保持し、24時間等で削除して再作成を許してはいけない。

### 10. キャッシュ・公開取り消し・負荷

- P0の個別作品、一覧、chunk、OG/PNGは `Cache-Control: no-store`。Next.jsのデータキャッシュや画像CDNへ私的本文を保存しない。公開一覧の速さはindex・件数上限で確保する。
- 内容を含まないoverviewと統計だけ最大30秒の共有キャッシュを許可する。asOfを返す。countの遅延を空枠の確定判断に使わない。
- clientの公開データはページ表示中だけ保持し、mutation後は対象chunk/作品を無効化する。再訪・タブ復帰時は再取得する。offlineキャッシュにUGC本文を入れない。
- 公開から非公開へ変えた後に、既存SNSの画像キャッシュ・他人が保存済みの画像まで回収できるとは表示しない。以後の自サーバー応答は現在設定へ即時追従させる。
- 後でCDNを導入する場合は、非公開化時の同期purge・cache key・失効失敗時の安全な応答を追加設計してから有効化する。
- 100万件のSELECT、巨大OFFSET、全件DOM化、全件Realtime購読を禁止する。地図は可視chunkと小さな先読みだけ取得する。
- chunkは最大400件で固定schema。非圧縮512KiBを通常応答の目標、4MiBを初期保護上限とする。文字列のバイト上限も適用する。超過時に一部の占有枠を黙って省略せず503で粗い表示へ戻し、取得失敗を空枠扱いしない。
- ランダム訪問は公開候補のbucket/keyset等で上限付き探索を行い、全件 `ORDER BY random()` を常用しない。対象なしは200 item:null。

### 11. エラーと初期レート制限

| HTTP / code | UIの扱い |
|---|---|
| 400 `INVALID_QUERY` / `INVALID_CURSOR` | URLやページング条件を修正する |
| 400 `INVALID_OTP` | コードまたは期限を確認し、必要なら再送する。本文下書きは保持 |
| 401 `AUTH_REQUIRED` / `SESSION_EXPIRED` | 下書きを保持し、再認証する |
| 403 `FORBIDDEN` / `ADMIN_REQUIRED` | 操作不可。権限情報や他人のIDを追加表示しない |
| 404 `NOT_FOUND` | 未存在・hidden・deleted・別world・他人の本人routeを同じ扱いにする |
| 409 `SLOT_TAKEN` | 下書きを保持し、近隣候補を選び直す |
| 409 `OWNER_LIMIT_REACHED` | 本人の既存絵馬へ誘導する |
| 409 `VERSION_CONFLICT` | 編集内容を保持し、現在データを取得して再確認する |
| 409 `IDEMPOTENCY_KEY_REUSED` | 同じkeyの別body。クライアント処理を修正する |
| 409 `WORLD_NOT_OPEN` | 期間/状態に応じて閲覧へ戻す。書き込み自動再送を続けない |
| 409 `POSTING_PAUSED` | 新規受付の一時停止。下書きを保持し、閲覧は継続できる |
| 409 `ACCOUNT_LINK_CONFLICT` | 同一UIDのメール追加を継続できない。勝手にアカウント切替しない |
| 422 `VALIDATION_ERROR` | fieldErrorsを表示。入力を消さない |
| 429 `RATE_LIMITED` | Retry-AfterとretryAfterSecondsを返し、待機後に本人が再試行 |
| 503 `TEMPORARILY_UNAVAILABLE` | 通信復旧後に同じ冪等性keyで再試行。下書きを維持 |

500系レスポンスにSQL、stack trace、メール、本文、秘密を含めない。requestIdでサーバーログと照合する。DBの制約名は許可リストでアプリerrorへ変換する。

初期のアプリ側制限は配置試行10回/分/UID、編集30回/10分/UID、通報5回/時/UID、画像生成30回/分/送信元、OTP要求は同一宛先60秒間隔を基本とする。Auth側上限は導入時の設定値も確認し、サービス側と両方を適用する。これは推奨初期値で、アクセス実績に応じて変更可能な設定とする。

分散実行に対応したDB/Redis等の共有ストアを使い、プロセス内Mapを本番制限にしない。IPは逆プロキシの信頼できる転送情報から取り、必要なら短期HMAC識別子を使う。共同利用回線のため、IPだけを本人クォータへ使わない。CAPTCHA/制限ストアが利用不能な本番変更要求は503で閉じる。デモ用in-memory adapterは明示的なdemo環境だけで動かし、本番設定不足を黙って代替しない。

### 12. P1/P2の拡張境界

#### P1: 無料共同エリア

- `groups`: id UUID v4（公開IDとして利用）、world_id、host_id、name（30書記素）、description（任意120書記素）、origin_x/origin_y、width=10/height=10、state=`open|closed|hidden|deleted`、created_at、updated_at、deleted_at、version。
- 正規URLは `/w/{worldSlug}/g/{groupPublicId}`。作成導線は `/w/{worldSlug}/new?group={groupPublicId}`。矩形はworld境界内に収め、origin_x/origin_yは0〜990。
- エリアはworld内の10×10の矩形。重複可・非排他的。枠の予約権、他人を追い出す権利、場所の販売権を付与しない。
- `group_memberships`: id UUID v4（membershipId。作品publicIdとは別の不透明ID）、group_id、ema_id、owner_id、state=`active|left|removed`、joined_at、version。activeに限りema_id uniqueで「1絵馬1group」。`(group_id,owner_id)` もuniqueにする。
- 参加は本人の明示操作。同worldで範囲内の本人絵馬だけ参加可。範囲外なら参加不可。座標移動や2枚目の作成で回避しない。
- 作成者は毎回確認済みメールの状態を検証。一般参加者は匿名可。group作成は1主催者・1worldにつきdeleted以外を1つまでとするpartial unique indexで制約する。
- 主催者は名称・募集状態・membershipの一覧除外だけ管理。他人の本文編集/削除、owner_only本文の閲覧、世界全体からの撤去はできない。
- 公開グループ一覧はpublic/active作品だけを返す。unlistedを所属一覧や参加履歴から列挙しない。主催者の除外後も元作品は存続する。
- world archivedでは新規group・参加・再参加・名称/説明変更を禁止。退出・募集締切・主催者による一覧除外・group削除は可能。
- closedは募集停止であり既存の公開一覧は存続。hiddenは運営の非表示で公開GETを404。deletedは解散で公開GETを404、名称/説明を消去し、所属だけを解除する。どの場合も主催者操作で元の絵馬を削除しない。
- hiddenのgroupを主催者がopen/closedへ変更して公開復帰させることはできない。主催者には削除だけを許可する。
- 主催者にremovedされた同UIDは同groupへ再参加不可。本人のleftはopen期間中なら再参加可。削除再作成した絵馬でも同UIDのremovedを回避しない。

P1の新規配置でgroupへ同時参加する場合は `groupId` をCreate入力へ追加し、同じDBtransactionでworld・group状態・座標範囲・本人所有を検証する。URLのgroupIdだけで所属を確定しない。P0ではこのキーを受け付けない。

P1のnearbyは任意のgroupを受け付け、候補をその矩形内に制限する。near対象がgroup範囲内ならその周辺、範囲外ならgroup中心を原点にする。グループが空き枠を事前に占有する処理は追加しない。

#### P1の追加API契約

以下はP1を実装する際の最小契約。prefixは `/api/v1`。変更APIはIdempotency-Key必須、本人/主催者の検証、Origin確認、同一transaction、409競合、no-storeをP0と同様に適用する。未開放時は404 `FEATURE_NOT_ENABLED`。

```ts
type PublicGroup = {
  publicId:string;worldSlug:string;name:string;description:string|null;
  originX:number;originY:number;width:10;height:10;
  state:'open'|'closed';version:number;
  memberCount:number;listedMemberCount:number;
  createdAt:string;updatedAt:string;
};
type GroupReceipt = {
  groupPublicId:string;version:number;
  result:'created'|'updated'|'deleted';
};
type MembershipReceipt = {
  groupPublicId:string;membershipId:string;
  state:'active'|'left'|'removed';membershipVersion:number;
};
type OwnerGroup = Omit<PublicGroup,'state'> & {
  state:'open'|'closed'|'hidden';
};
type HostMembership =
  | {kind:'listed';membershipId:string;version:number;ema:PublicEma}
  | {kind:'unavailable';membershipId:string;version:number};
type Fulfillment = {state:'pending'|'fulfilled';fulfilledAt:string|null};
```

PublicGroupにhost UID/メールは含めない。memberCountはactive所属かつactive絵馬（unlisted含む）、listedMemberCountはさらにpublicの件数。両者の違いから非公開IDを列挙するAPIは作らない。

| POST `/admin/groups/{groupId}/moderation` | 管理者。`{action:'hide'\|'restore'\|'delete',reasonCode,expectedVersion}`。restoreはclosedへ。監査を保存し200 `{receipt:GroupReceipt}` |
| PATCH `/me/emas/{id}/fulfillment` | 本人。`{state:'pending'\|'fulfilled',expectedVersion}`。world open・active絵馬のみ。200 `{receipt:MutationReceipt}` |

P1のOwnerEmaに `groupMembership:{groupPublicId,membershipId,version}|null` と `fulfillment:Fulfillment` を追加する。groupMembershipは現在のactive所属だけ。PublicEmaには `fulfillment:Fulfillment` を追加し、本文の秘密設定は引き続き厳守する。成就日時はサーバー現在時刻、pendingへ戻すとnull。成就変更は原本versionと投影を同じtransactionで更新する。

参加時はworld→group→ema→membershipの順など固定したロック順を使用する。別groupへの同時joinはactive unique制約で1つだけ成功させる。同groupに既にactiveなら既存receiptを返し、人数を二重加算しない。グループ削除とjoinが競合しても削除済みgroupのactive所属を作らない。絵馬delete時は所属と成就情報も同じtransactionで無効化/削除する。

別groupへの移動は本人が旧所属をleftにしてから新しいgroupへjoinする。自動移動やatomicな所属差し替えはP1に実装しない。後のjoinが失敗しても旧所属へ勝手に戻さない。

P1でmoderation_auditを `subject_type + subject_id` へ拡張し、groupの管理操作も記録する。group非表示は絵馬の非表示と分け、所属する他人の作品を一括hiddenにしない。

追加エラーは403 `VERIFIED_EMAIL_REQUIRED`、403 `GROUP_MEMBERSHIP_REMOVED`、409 `GROUP_OWNER_LIMIT_REACHED`、409 `GROUP_CLOSED`、409 `OUTSIDE_GROUP`、409 `ALREADY_IN_GROUP`、409 `EMA_NOT_ACTIVE`。versionの不一致は既存 `VERSION_CONFLICT`。権限のない主催者操作はFORBIDDEN、見えないgroup/所属はNOT_FOUND。座標外へ新しい作品を自動配置して解消しない。

#### P1: 成就状態 / P2: 決済

成就は `fulfillments` を別テーブルで追加し、ema_id、状態、timestampのみ保持する。元の願い事・公開設定・作品IDを保持し、追記本文・写真はP1にも含めない。本人のみopen期間中に変更可能で、archivedでは変更不可。unlisted/owner_onlyの公開規則を引き継ぐ。P0では未完成列・UIを開放しない。

P2はorders/payments/entitlementsを追加し、商品カタログをサーバーで管理する。価格・design権限をクライアント入力から信用しない。購入完了画面への遷移だけでは権利を付与せず、検証済みWebhookと一意なイベントIDで付与する。購入・返金・退会時の表示はP2の別受入条件とする。

装飾権利はowner+world+designに紐づけ、同じ年に削除して作り直しても利用できる。主催者プランはgroup+worldに紐づき、枠の独占権には変えない。価格・販売期間・返金条件は本公開前に確定する初期案として扱う。

### 13. 実装完了の受入条件

- 同座標へ異なる100リクエストを同時送信して成功が1件。敗者の本文は残り、counter/occupancy/projectionに孤児がない。
- 同UIDが別座標へ同時配置して成功が1件。hiddenでも2枚目を作れず、delete後は新規IDで配置可能。
- 同じkey/bodyの同時再送は同じreceipt。別bodyは409。応答喪失後の再送と削除後の旧create再送でも二重作成しない。
- 他人のUUID/ownerId偽装、未検証Cookie、未公開schema/Data API直アクセス、公開関数へのEXECUTEで本人操作を突破できない。
- owner_onlyの固有テスト文言が公開API/HTML/RSC/OG/PNG/chunk/一覧/エラー/ログへ含まれない。本人GETでは正しく読める。
- unlistedのpublicId/nickname/本文が地図・一覧・random・group一覧へ出ず、直接URLだけは設定通り表示される。
- UID A/Bの要求を同じ接続プールで交互実行し、SQL context・SSR・Cookie・キャッシュが混線しない。
- 本文編集中に別端末から更新/削除して、古いexpectedVersionで上書きできない。公開範囲縮小後の新規取得に旧本文がない。
- メール追加前後でUIDと所有作品が同じ。別端末OTP復帰、OTP失敗、既存メール競合、匿名セッション消失が定義通り動く。
- JST締切の直前/直後、world archived、制限ストア停止、DB接続切断で不変条件を保つ。
- DB制約・RLS・migrationをローカルまたは隔離テストDBで検証し、lint/typecheck/必要な統合・E2E検証結果を残す。本書作成時点ではアプリとSQLを実行検証したとは扱わない。

## えまのわ 共有と共同参加仕様

このパートは、絵馬を他の人に見せる機能、近くへの招待、P1 の共同エリア、成就報告を定義する。P0 では無料の共有と招待までを実装する。プラットフォームへの自動投稿や、本人の操作を伴わないメッセージ送信は行わない。

### 1. フェーズと達成する体験

| フェーズ | 実装するもの | 利用者の体験 |
| --- | --- | --- |
| P0 | 個別URL、X/LINE共有、URLコピー、PNG保存、近くへの招待 | 自分の一枚を紹介し、友達にも近くに掛けてもらう |
| P1 | 無料の共同エリア、グループ招待、成就報告 | 仲間で願いを集め、あとから結果を伝える |
| P2 | 特別デザイン、主催者用の表示・記念成果物 | 企画を自分たちらしく整える |
| P3 | 自動生成の短い動画、外部埋め込み等 | 実績を見て追加する |

通常の個別URL、招待リンク、基本の共有PNGを有料にしない。収益化の範囲は `06_MONETIZATION_ROADMAP.md` に従う。

P0 は `ENABLE_GROUPS=false`、`ENABLE_FULFILLMENT=false`、`ENABLE_PAYMENTS=false`。サーバーの設定を正本とし、クライアントのクエリー値や表示切替で未公開のAPI機能を有効にしない。

### 2. URLと権限

#### 2.1 公開URL

公開URLは `/w/{worldSlug}/e/{publicId}`。`publicId` は UUID とする。表示番号・所有者ID・メールアドレス・編集用情報を識別子の代わりに使わない。

- 同じ絵馬を編集しても公開URLは変わらない。
- 削除後の公開URLは別の作品へ流用しない。
- 地図の枠が再利用されても、古い作品URLは新しい作品を指さない。
- URLを知ることと、その絵馬の編集権限を持つことを区別する。
- `unlisted` はURLを知っている人が閲覧できる。パスワード保護や本人限定という意味ではない。

#### 2.2 友達の近くへ招くURL

招待先は `/w/{worldSlug}/new?near={publicId}`。所有者情報や編集用トークンを付けない。

対象作品が現在も有効なら、作品を確認できる位置へ移動し、その近くの空き枠を選べる状態にする。対象の本文が `owner_only` なら、招待先にも本文を出さない。

「近く」は空き枠候補の案内であり、隣の枠の予約ではない。誰かが先に掛けた場合は通常の `409` 競合処理へ進む。

空き候補は `GET /api/v1/worlds/{worldSlug}/nearby?near={publicId}` でサーバーから最大8枠取得する。案内時の空きと保存時の空きが同じとは限らない。

#### 2.3 リンクの優先順位

| 入力 | 解釈 |
| --- | --- |
| `near` のみ | 有効な対象作品の近くを案内 |
| `x`,`y` のみ | 範囲内の座標を初期候補として案内 |
| `near` と `x`,`y` | `near` を優先 |
| `near` が削除済み・非表示・無効 | 原文を出さず、対象年の通常の作成画面へ。理由を短く表示 |
| P1 の `group` 指定 | グループの範囲を作成場所の制約にする |
| `group` と `near` | 対象がグループ範囲内なら近くを案内。範囲外ならグループ中心を使う |

不正なクエリー値は無視するか入力エラーにし、別ドメインへのリダイレクト先として使用しない。世界をまたぐ `near` や `group` は受け付けない。

### 3. P0の共有操作

共有シートには次を表示する。

1. Xで共有
2. LINEで送る
3. リンクをコピー
4. 画像を保存
5. 近くに友達を招く

共有シートを開くと、実際に共有するタイトル・URL・カードの見た目を確認できる。本人の非公開本文を、そのまま共有入力に初期設定しない。

#### 3.1 共有文章

通常共有の初期文言：

> えまのわに、{worldYear}年の願いを掛けました。\n{publicUrl}\n#えまのわ

近くへの招待の初期文言：

> えまのわに願いを掛けました。よかったら、近くにあなたの願いも掛けてね。\n{inviteUrl}

上記の `\n` は実装時には改行として扱い、`worldYear` は対象の世界の設定から取得する。本人がSNSの投稿画面で編集できるようにする。願いの原文は共有文章へ自動挿入しない。

#### 3.2 X

- サーバーでXのアカウント連携や投稿権限を取得しない。
- 公式の共有用URL仕様を実装時に確認し、テキストと公開URLをエンコードして投稿画面へ渡す。
- 投稿を確定するのは利用者本人。
- 画像保存とURL共有を用意する。共有用URLに画像が必ず自動添付されるとは扱わない。
- X側がOGカードを表示しない場合でも、リンクを開けば公開詳細へ到達すること。
- 共有ボタンクリックを「投稿完了」として計測しない。

#### 3.3 LINE

- 公式のURL共有仕様を実装時に確認する。
- 基本機能は公開URLまたは招待URLを利用者が送ること。
- LINEの友達一覧の取得、公式アカウントの追加、メッセージの自動配信をP0の必須条件にしない。
- 端末環境で共有画面を開けない場合、URLコピーへ切り替えられること。

#### 3.4 コピー・ネイティブ共有

- コピー後は「リンクをコピーしました」と読み上げ可能な完了表示を出す。
- Clipboard APIが使用できなければ、選択可能なURL欄を表示する。
- 端末の共有メニューを補助として使ってもよい。利用できないブラウザでも通常の共有操作を残す。
- ネイティブ共有で画像ファイルを渡せるかは実行時に判定し、未対応なら画像保存とURLコピーを案内する。

### 4. 共有カードと画像

#### 4.1 画像の基本仕様

| 種類 | P0での扱い | 内容 |
| --- | --- | --- |
| OGカード | 必須、1200×630pxを基本とする | サービス名、絵馬、対象年、番号、公開可能な本文・表示名 |
| 保存用PNG | 必須、1080×1080pxを基本とする | 絵馬を中心に、サービス名、年、番号、短い導線 |
| 無料グループカード | P1、標準OG・保存PNG | 名称、年度、参加数、匿名の絵馬モチーフ。参加者の本文・表示名は含めない |
| 全体の記念PNG | P2 | 最大100枠の公開所属絵馬をまとめる。商品範囲は06に従う |
| 印刷用PDF等 | P3の別仕様 | 需要と仕様が決まるまで実装しない |

公開カードは公開用DTOから描画する。生のDB行や本人用DTOを直接テンプレートに渡さない。

画像の取得先は `GET /api/v1/worlds/{worldSlug}/emas/{publicId}/image?variant=og|square`。`messageVisibility=owner_only` の公開用DTOでは `messageText=null` とし、別のプロパティへ本文を移して回避しない。

- 日本語フォントと絵文字の欠落を確認する。
- 長い願いは枠内で改行し、許容文字数内でも画像が崩れないようにする。
- 共有画像に外部URLを利用者が自由に埋め込める機能はP0に設けない。
- 画像生成では利用者の入力をHTMLや実行コードとして扱わない。
- 公開できない場合は空文字の差し込みで済ませず、定型の絵馬表面を描く。
- 周囲の絵馬を画像に含める場合、他人の本文や表示名を描画しない。P0は装飾用の匿名シルエットでよい。
- 画像を生成できない場合でも、URLの共有は利用できるようにする。

#### 4.2 掲載範囲と画像の対応

| `visibility` | `message_visibility` | 地図・公開一覧 | 個別URL・画像 |
| --- | --- | --- | --- |
| `public` | `public` | 公開用カード | 公開本文を表示可 |
| `public` | `owner_only` | 本文のないカード | 本文のないカード |
| `unlisted` | `public` | ID・本文・表示名を出さない占有表示のみ | URLを知る人には公開本文を表示可 |
| `unlisted` | `owner_only` | ID・本文・表示名を出さない占有表示のみ | 本文のないカード |

`unlisted` のページと画像には検索インデックスを抑止する指定を付ける。ただし、検索抑止をアクセス制御の代わりにしない。

#### 4.3 編集・削除・キャッシュ

- P0 の個別詳細・一覧・地図チャンク・画像は `Cache-Control: no-store` とし、アプリ側で公開本文の共有キャッシュを作らない。
- 画像取得時に現在の状態・公開範囲を確認する。古いURLや任意のクエリー値を指定しても、非公開化前の本文を再生成しない。
- 公開範囲変更、削除、運営非表示では、表示中のアプリ内データを無効にし、次の取得で現在の状態へ更新する。
- 削除済み・非表示の画像URLは原文のない代替画像または非存在レスポンスにする。
- 本人しか見られない画像を一般公開ストレージへ保存しない。
- SNSが既に取得した画像や、他人がダウンロードした画像の回収までは保証しない。

### 5. 友達が招待リンクを開いたとき

#### 5.1 初めて参加する人

1. 招待元の絵馬とその近辺が表示される。
2. 「この絵馬の近くに、あなたの願いも掛けてみませんか」と案内する。
3. 空き枠を選び、通常の作成フローへ進む。
4. 保存後は自分と招待元の位置を確認できる。
5. 自分の近くへ次の人を招待できる。

閲覧のために会員登録を要求しない。作成時のゲスト認証・一枚制限は通常と同じ。一枚制限は同一の `Auth UID × world` に対して適用し、別端末のゲスト同士を同一人物として識別する設計にはしない。

#### 5.2 すでに絵馬がある人

- 同じ年に `active` または `hidden` の絵馬があれば、二枚目を作れない。
- 「この年の絵馬は、すでに掛けています」と表示し、自分の絵馬と招待元を見る導線を出す。
- P0/P1では位置移動を提供しない。招待を理由に本人の作品を勝手に移動しない。
- 別の年にしか絵馬がない場合は、対象年で新規作成できる。

#### 5.3 対象が見られない・近くが埋まっている

- 招待元が削除済み・非表示なら、その本文や旧表示名を復元表示しない。
- 「招待された絵馬を表示できませんでした。この年の絵馬掛けから場所を選べます」と案内する。
- 近くが埋まっていれば、探索半径を広げて候補を提示する。
- 最終的な場所は本人が確認して選ぶ。勝手に遠い場所へ投稿しない。
- 全枠が埋まっていれば新規投稿を停止し、閲覧と自分の既存作品の操作を残す。

### 6. P1 無料の共同エリア

#### 6.1 共同エリアの単位

- グループは同じ世界の中の10×10枠の矩形とする。
- グループごとに別の世界や新しい100万枠を作らない。
- 矩形は場所を紹介する範囲であり、100枠の予約・排他的な所有ではない。
- 異なるグループの矩形は重なってよい。位置が重なっても所属や主催権限は統合しない。
- 一般利用者も同じ場所の空き枠へ通常の条件で掛けられる。
- 同じ範囲にあることと、グループに参加していることを区別する。
- グループ所属は04の所属レコードによる明示的な参加とする。近くにある他人の絵馬を勝手に参加者に加えない。
- 一つの絵馬が所属できるグループは一つ。本人が離脱・別グループへ加入する操作は可能。

#### 6.2 グループの情報

| 項目 | 仕様 |
| --- | --- |
| 公開識別子 | `groupPublicId`、UUID |
| 対象年 | 一つの `world` に所属 |
| 名称 | 必須、30書記素以内、プレーンテキスト |
| 説明 | 任意、120書記素以内、プレーンテキスト |
| 範囲 | 左上 `x`,`y` と幅10・高さ10、世界内に収まる |
| 主催者 | 一人の所有者。無料作成はメール確認済みアカウントに限定 |
| 募集状態 | 募集中・締切・削除 |

P1は同一のメール確認済み `Auth UID × world` につき、有効なグループを一つまでとする。主催者の絵馬をグループへ自動加入させない。追加テーマ、展示、全体の記念出力はP2。ロゴのアップロードはP3の別仕様とする。P2でも矩形を独占する権利や、他人の作品・本文への管理権は販売しない。

#### 6.3 参加の流れ

グループ公開URLは `/w/{worldSlug}/g/{groupPublicId}`。参加ボタンは `/w/{worldSlug}/new?group={groupPublicId}` へ進む。

| 利用者の状態 | 動作 |
| --- | --- |
| 対象年の絵馬なし | グループ範囲内の空き枠を選び、新規保存と同時に参加 |
| 自分の絵馬が範囲内 | 本人が確認してグループへ加入。作品は増やさない |
| 自分の絵馬が範囲外 | 「あなたの絵馬はこのエリアの外にあります」と説明。二枚目作成・自動移動は行わない |
| 別グループに所属 | 新しい加入条件を確認し、本人が現在のグループを退出してから新規加入する。P1で自動的な所属移動は行わない |
| 募集締切 | 閲覧可能。新しい加入は不可 |
| 空き枠なし | 既存の範囲内絵馬の加入は可。新規作成は不可 |
| 世界がアーカイブ済み | 新規作成・加入・別グループへの所属変更は不可。閲覧、本人の退出、主催者による所属除外は可能 |

保存時にサーバーでも世界、矩形範囲、募集状態、所有者、一枚制限を確認する。ブラウザの案内だけで参加を許可しない。退出と別グループ加入は別操作であり、加入が失敗しても旧所属が自動復元されるとは表示しない。主催者による除外は同じUIDのそのグループへの再参加を禁止するが、元の絵馬と世界の場所は保持する。

#### 6.4 表示と主催者の権限

- グループの公開一覧は、加入した `public` の有効な絵馬だけをリンク付きで表示する。
- 参加数は明示的に所属する有効な絵馬の件数。矩形内に存在するだけの他人の絵馬を数えない。
- `unlisted` の参加絵馬は件数と占有表示のみ。ID、本文、表示名、個別URLを公開一覧へ出さない。
- `owner_only` の本文は、主催者にも渡さない。
- 主催者は名称・説明・募集状態を変更し、グループの参加一覧から絵馬を除外できる。
- 除外は所属関係を外す操作。作品の本文、座標、所有権、全体の地図への掲載を変更しない。
- 主催者は参加者の絵馬の編集・削除・有料化・非公開本文の閲覧を行えない。
- 参加者は自分の所属を外せる。グループを削除しても、参加者の絵馬そのものは残る。
- グループ主催者向け画面も認可が必要。公開UUIDを知っているだけで管理できない。

#### 6.5 無料の共有カードと記念出力

- グループの参加URLコピーは無料。
- P1の無料グループカードは、名称・年度・参加数・匿名の絵馬モチーフだけを描く。参加者の本文・表示名・個別URLを並べない。
- 無料カードは標準のOG（1200×630px）と保存PNG（1080×1080px）を提供する。P2を購入しなくても利用できる。
- P2の記念PNGは、最大100枠の `active` / `public` の所属絵馬をまとめる別の成果物。無料カードを有料へ置き換えない。
- 記念PNGにも `unlisted` の内容や `owner_only` の本文を埋め込まない。アーカイブ後の新規生成は06の期間条件に従う。
- 参加者がグループに加入するときに、グループページと将来の記念画像での見え方を説明する。
- 第三者の絵馬を運営の広告・紹介記事へ自動掲載する機能は作らない。
- 主催者が独自に配信する場合も、画面には公開用DTOだけを使用する。

### 7. P1 成就報告

- 本人が自分の絵馬に「叶いました」の状態を付けられる。
- P1で保持するのは成就状態と更新日時だけ。報告本文・写真・コメントの追加は実装対象外とする。
- 願いの原文を上書きしない。成就状態は原文とは別に保持し、本人が状態を戻せるようにする。
- 成就表示の公開範囲は元の絵馬の掲載範囲を超えない。元の本文が `owner_only` なら、成就後のページ・画像にもその本文を出さない。
- 成就後の共有も本人がプレビューして実行する。状態変更をきっかけに自動投稿しない。
- 通知やメールによる再訪案内はP1の必須機能にしない。導入する場合は本人の希望と解除方法を用意する。
- 世界がアーカイブ済みなら、成就状態も変更できない。アーカイブ後の成就更新は、必要になった時点で別仕様として定義する。

### 8. 計測

P0で最低限、以下のイベントを計測できるようにする。願い本文・表示名・メールアドレス・認証情報をイベントに含めない。

| イベント | 意味 |
| --- | --- |
| `ema_created` | サーバーで新規作成が確定した |
| `share_opened` | 共有シートを開いた |
| `share_clicked` | X/LINE等の共有先を選んだ。投稿完了とは異なる |
| `link_copied` | 通常リンクまたは招待リンクをコピーした |
| `share_image_downloaded` | 画像の保存操作を実行した |
| `invite_landed` | 招待リンクから有効な作成画面へ到達した |
| `invite_ema_created` | 招待経由の新規作成が確定した |
| `group_joined` | P1で所属の追加・変更が確定した |

計測はアプリの主操作を失敗させない。計測サービスへの送信が失敗しても、投稿・共有・画像保存を利用できるようにする。招待の効果はクリック数だけでなく、招待経由の訪問と作成完了で判断する。

### 9. 受入条件

- SHARE-01：X/LINEの投稿や送信を確定する前に、本人が内容を確認できる。認証情報は共有URLに含まれない。
- SHARE-02：SNS側のカード表示に依存せず、URLから対象の絵馬へ到達できる。
- SHARE-03：日本語80書記素、改行、絵文字を含む公開本文で、カード画像が崩れない。
- SHARE-04：公開設定の4通りで、地図、一覧、詳細、OG、保存PNGが表の規則と一致する。
- SHARE-05：本人だけの本文が、公開レスポンス、画像、キャッシュ、分析イベントに存在しない。
- SHARE-06：非公開化・削除後に旧画像URLへアクセスしても、アプリ側は以前の本文を返さない。
- SHARE-07：招待先の作成で同じ年に二枚目を作れない。競合時に文面が保持される。
- SHARE-08：無効な招待、全枠満杯、受付終了でも、画面が無限読み込みにならない。
- GROUP-01：P1の新規参加はグループの範囲内に限られ、一般の場所取得と同じ競合防止が働く。
- GROUP-02：既存の範囲内絵馬は加入だけでき、範囲外絵馬の自動移動や二重作成は起きない。
- GROUP-03：主催者による除外・グループ削除で、参加者の絵馬本文や所有権が変わらない。
- GROUP-04：グループの公開一覧・集合画像・主催者画面から、非公開本文を取得できない。
- GROUP-05：未実装のP1/P2機能はP0画面に露出しない。参加・招待に決済を要求しない。

## Part 06 — 収益化と後続開発

### 1. このパートの位置づけ

P0/P1の無料体験が完成してから実装する。価格・商品内容は**検証のための初期案**であり、ユーザーが最終決定した料金表ではない。P0に決済ページ、購入を装うボタン、未実装の売り切れ表示を置かない。

基本方針は、願いを書いて掛ける参加体験を無料にし、見た目や主催者の作業を便利にする機能を販売すること。願いの成就、優先的なご利益、他人の非公開内容へのアクセスを商品にしない。

### 2. 商品の初期案

| 商品 | 価格案 | 単位 | 提供するもの |
|---|---|---|---|
| 基本の絵馬 | 無料 | 1アカウント×1年度×1枚 | 作成、基本デザイン、場所、共有、編集・削除 |
| 無料グループ | 無料 | 主催者1アカウント×1年度につき有効1つ | 10×10の範囲、招待URL、所属の管理 |
| 特別デザイン | 500円（税込表示の案） | 1所有者×1年度×1デザイン | 購入した年度で使える絵馬の外観 |
| 主催者プラン | 4,980円（税込表示の案） | 1グループ×1年度 | 選択式テーマ、展示画面、公開絵馬の記念出力、集計 |

金額は整数の日本円でサーバーに保持する。固定価格商品のみとし、P2初回にサブスクリプション・クーポン・ポイント・投げ銭・複数通貨を追加しない。決済手数料や収益見込みは、販売時点の条件と実績で別途計算する。

### 3. 特別デザイン

#### 3.1 権利

- 権利は `owner_user_id + world_id + design_id` に紐づく。
- 購入によって絵馬の枚数や枠数は増えない。
- 同じ年度の自分の絵馬を削除して作り直した場合も権利を保持する。
- 同じデザインを購入済みなら再購入ボタンを表示せず、サーバーも重複購入を拒否する。
- 別の年度では別商品として扱う。購入前に年度を明記する。
- 投稿を削除しても、注文履歴は必要な取引記録として別管理する。願い本文を注文に複製しない。
- 新規購入とデザイン変更はworldがopenの間のみ。受付終了後は既に適用済みの外観をアーカイブに保持する。

P2ではサーバーに同梱した定義済みSVG等を販売する。自由アップロード、外部URLからの画像取得、実行可能なSVGの持ち込みを認めない。無料と有料の差は見た目であり、公開範囲や編集権限は変わらない。

#### 3.2 UI

デザイン一覧に無料・価格・対象年度・購入済みを表示する。購入前の見た目をプレビューできる。決済完了後は権利の反映を確認してから「使う」を有効にする。画面が戻っただけで購入済みにしない。

### 4. 主催者プラン

#### 4.1 P2の提供範囲

1. 定義済みの背景テーマとアクセント色を選択する。
2. 大画面展示用の読み取り専用ページで、所属する公開絵馬を順番に表示する。
3. 公開絵馬をまとめた記念PNGを生成する。グループ最大100枠を扱い、長文は個別ページへの導線を併記する。
4. 参加数と公開絵馬数の集計、公開情報のみのCSV出力を提供する。P2初回の列は表示番号、分類の列挙値、作成日時、成就状態、正規URLに限定し、本文・表示名を含めない。将来利用者入力の文字列を出力するときは、先頭の `= + - @` 等が表計算ソフトで数式として実行されない処理を追加する。

P1で無料のグループ公開ページ・簡単な共有カードを作る。無料カードは名称・年度・参加数・匿名の絵馬モチーフで、参加者の本文・名前を含めない。P2の記念出力は全員の公開絵馬をまとめる大きな画像であり、無料の共有カードを使えなくするものではない。ロゴアップロード・印刷用PDFはP3の別仕様とする。

#### 4.2 権利の境界

- グループは同じ世界の10×10の範囲を使う。購入しても範囲は広がらず、非参加者を排除する土地にはならない。
- 主催者の権利は対象グループだけに適用される。別グループに譲渡しない。
- 非公開本文、URL限定絵馬のID・本文・名前、参加者のメールを展示・画像・CSVへ出さない。
- 対象は `active` かつ `visibility=public` の所属絵馬。`owner_only` の本文は隠す。非表示・削除後は新規出力に含めない。
- 公開状態変更後も自サーバーが古い画像を配信しない。P0/P1と同じ公開投影・失効方針を用いる。
- 主催者は他人の絵馬を編集・削除できず、所属から外すことだけができる。
- 購入には確認済みメールを必要とする。参加者のメール登録は必須にしない。

#### 4.3 期間

商品は対象年度の受付終了までの主催者向け機能と、その後の読み取り専用アーカイブに適用する。永久保存を約束しない。新しい記念出力とCSV生成はworldがopenの間のみ。アーカイブ後は購入済みテーマと読み取り専用展示を、サービスの公開保存方針の範囲で維持する。

販売終了日は `sales_close_at` で持ち、初期案はworld終了の30日前。終了直前の購入で利用期間が極端に短くならないよう、購入画面に使える期間を表示する。公開前に保存方針を確定するまで本番販売を有効にしない。

### 5. 購入者認証

購入時はP0のメール連携を先に案内する。匿名利用者を新しいUIDに置き換えず、既存の絵馬を持つUIDに確認済みメールを結びつける。

既存アカウントと競合したときに、メール文字列の一致だけで絵馬・グループ・権利を移動しない。04のログインと競合方針に従う。商品を買ったあとに本人確認できない状態を作らない。

### 6. 決済の実装契約

初期案はStripe Checkoutの単発決済を用いる。実装時に現行SDKと対応APIを確認し、バージョンを固定する。独自のカード入力画面やカード情報の保存は行わない。[Stripe Checkout公式ガイド](https://docs.stripe.com/payments/checkout)

#### 6.1 サーバーが持つ情報

P2 migrationで次の用途のテーブルを追加する。実際のSQL名・型は04の命名と合わせる。

| テーブル用途 | 主な情報・制約 |
|---|---|
| 商品定義 | sku、種類、円価格、対象年度/デザイン、販売期間、有効状態、環境別Price ID |
| 注文 | UUID、購入者UID、対象、価格スナップショット、状態、Checkout Session ID（unique）、Payment Intent ID |
| 決済イベント | Stripe event ID（unique）、種類、処理状態、時刻。本文の全文保存は不要 |
| 権利 | 購入者またはグループ、年度、商品、付与元注文、active/revoked、権利キーunique |
| 決済処理の再試行 | 注文ID、処理種別、試行回数、次回時刻、最後のエラー種別 |

注文・メール・支払情報を公開APIや地図データに混ぜない。イベントや注文のログにカード情報、願い本文、秘密の共有URLを記録しない。

#### 6.2 作成API

`POST /api/v1/checkout/sessions`

入力は `sku`、`worldSlug`、対象の `groupPublicId` 等、`Idempotency-Key`。`amount`、`owner_user_id`、Stripe Price IDをクライアントから採用しない。

サーバーが次を検証する。

1. 決済機能が有効で、購入者のメール確認が済んでいる。
2. 商品・world・価格・販売期間が有効で、対象の所有権がある。
3. 既に同じ権利を保有しておらず、同じ商品の進行中注文がない。
4. 戻り先は設定した `APP_ORIGIN` 内の固定ルートである。
5. DBに注文を記録し、注文IDをキーにStripeの冪等作成を行う。

購入者・SKU・world・対象を組み合わせた購入単位ごとに、注文作成をDBロックまたは有効注文のpartial unique制約で直列化する。別の冪等キーや別端末で同時に要求されても、進行中注文は一つだけにする。権利のunique制約だけでは二重決済を防げない。

まずDBで `initializing` の注文を一意に確保し、ネットワーク越しのStripe呼出しは長いDBトランザクションの外で行う。同じ注文IDをStripeの冪等キーに使い、タイムアウト後も同じ注文の作成・照合を再試行する。結果不明の注文を破棄して新しい支払先を発行しない。

既存の進行中注文があるときは、利用できる同じCheckout URLを返す。未生成なら202の準備中状態を返す。失効させて新規注文に置き換えるときは、以前のセッションが未払いで確実に失効したことを確認し、同時に支払えるセッションを増やさない。API再試行やブラウザの二重クリックを二重注文にしない。

#### 6.3 完了の扱い

購入後ページは注文IDを受け取り、所有者限定の `GET /api/v1/orders/{orderId}` で状態を確認する。「支払いを確認しています」「購入済み」「失敗」「期限切れ」を区別する。未確認状態で再購入を促さない。

支払処理の根拠は、署名を検証したWebhookとStripe APIで確認した決済状態である。成功ページへの到達だけを権利付与の根拠にしない。公式のイベント処理案内に合わせる。[Stripeの支払後イベント](https://docs.stripe.com/payments/existing-customers?platform=web&ui=stripe-hosted)

#### 6.4 Webhookと権利付与

`POST /api/v1/webhooks/stripe`

1. 生のリクエスト本文で署名を検証する。検証前にイベント内容を信用しない。
2. 接続環境・対象アカウント・イベント種別を確認する。
3. 注文とCheckout Sessionの関連をDBから確認し、必要な現在情報をStripeから取得する。
4. 支払済み、金額、通貨、商品、購入者、対象年度を照合する。
5. DBトランザクションでイベントの重複排除、注文のpaid化、権利の一度だけの付与を行う。
6. 後続処理に必要なものは耐久キュー/DBジョブに記録し、記録成功後に2xxを返す。メモリー上の非同期処理だけで受領済みにしない。

署名検証・重複配信・順不同配信への対応はStripeの公式ガイドに従う。[Webhook公式ガイド](https://docs.stripe.com/webhooks)

`checkout.session.completed` を受けても支払状態が未完了なら権利を付与しない。遅延決済を有効にする場合は `checkout.session.async_payment_succeeded` / `checkout.session.async_payment_failed` を扱う。失効・失敗の後に遅れて成功通知が来た場合は、イベントの順番だけで決めず、実際の支払状態を再照合する。

同じイベントの再送だけでなく、別event IDで同じ注文の成功が届いても二重付与しない。署名不正は4xx、処理前の一時障害は再試行可能な応答とする。処理済みイベントの再送は成功を返す。

### 7. 返金と支払後の例外

- P2は全額返金を標準フローとする。返金が成功したことを確認して権利をrevokeする。
- デザイン権利の取消時は絵馬を削除せず、適用中なら `basic_wood` に戻す。これはarchivedでも許可する権利取消のシステム処理で、一般利用者のデザイン編集権限を広げない。version・公開投影・関連revision・監査を同一トランザクションで更新する。
- 主催者プランを取り消しても無料グループ・参加者の絵馬は残す。
- 一部返金は運営確認とする。権利は維持し、全額返金になるまで自動取消ししない。この挙動を運営手順に書く。
- 返金処理が失敗・保留なら、成功を装わず取引状態を表示する。
- チャージバック・決済取消しは調査対象として管理画面に出し、同じ記録への重複反映を防ぐ。
- 支払後にworldが閉じた場合、成立済み注文への付与自体は行う。ただし未使用の商品で提供ができない場合の返金導線を設ける。
- 注文の状態照合ジョブを用意し、Webhookが届かなかった注文を回復する。認証された運営ジョブだけが実行する。

具体的な返金条件・販売者表示は運営者の実際の提供条件に合わせて確定し、商品画面と矛盾させない。架空の販売者・住所・問い合わせ先を本番に載せない。

### 8. 本番課金を有効にする条件

`ENABLE_PAYMENTS=false` を初期値とする。次を満たして初めて有効化する。

- 実際の商品範囲、価格、提供期間、保存方針、返金条件が決まっている。
- 本番用の商品IDと環境が一致し、テスト鍵・本番鍵を混同しない。
- メール連携と再ログインで同じ絵馬・グループ・購入権利に戻れる。
- 決済成功・失敗・キャンセル・Webhook遅延・再送・順序逆転・返金を検証済み。
- 注文・権利・イベントにunique制約があり、複数インスタンスでも二重付与しない。
- 運営者が注文照合と返金の手順を実行できる。
- サーバー側で無効な機能のAPIを拒否する。ボタンを隠すだけにしない。

機能フラグを停止しても、既存購入権利の表示とWebhook・返金・注文照合は止めない。フラグは新規販売を止めるためのものとする。

### 9. 将来の収益化

| 案 | 採用を考える条件 | 追加仕様が必要な点 |
|---|---|---|
| 記念ポスター・実物の絵馬 | 保存・贈答への要望がある | 住所、制作、配送、返品、画像の利用範囲 |
| スポンサー | 実際の参加規模と対象層が分かる | 広告表示、掲載期間、願いとの分離 |
| 神社・地域との企画 | 提携先と実施内容が決まる | 役割、申込、金銭、祈祷・奉納の実態の表示 |
| 年度をまたぐ個人アーカイブ | 再訪需要が見える | 保存期間、解約時、削除、購入年度の取り扱い |

これらはP0/P1/P2の完成条件に含めない。初期版の参加・共有実績から順序を決める。

## Part 7　実装順序と品質確認

このパートは、Codexが実装を進める順序、各段階の完成条件、公開前に確認する動作を定義する。P0を一度に作り切ろうとせず、動く範囲を増やしながらデータの整合性と公開範囲を検証する。

### 1. 実装の原則

- 機能・権限・APIの矛盾は、[Part 4](#part-04) の契約へ戻って解消する。文言だけで不具合を隠さない。
- テスト用データ、接続のない画面、実DBへ保存した状態を区別する。
- 実際に保存できていないのに、投稿・メール送信・購入・共有の成功を表示しない。
- 型チェック・静的解析に加えて、投稿から取得までの実際の経路を確認する。
- サービスの外観を似せるだけのテストを増やさない。同時投稿、権限、公開範囲、再送、主要な利用の流れを優先する。
- 複数のブラウザー利用者は、異なる認証セッションで確認する。同じログインの別タブだけでは権限の確認にならない。
- 外部サービスをまだ設定できない場合も、データ契約とローカルの検証を進め、未接続項目と残った検証を正確に記録する。

### 2. P0の段階別実装

#### A　土台と契約

実施すること：

- Next.js・TypeScriptのプロジェクト、フォーマット、型チェック、ビルド手順を用意する。
- world、絵馬、公開DTO、所有者DTO、エラーの型を定義する。
- 環境変数の例を値なしで用意し、秘密鍵をクライアントへ含めない構成にする。
- `2027` worldとデザイン `basic_wood` を設定から扱えるようにする。
- `ENABLE_GROUPS=false`、`ENABLE_FULFILLMENT=false`、`ENABLE_PAYMENTS=false` をサーバー設定の正本とし、クライアントには秘密を含まないcapabilitiesだけを渡す。
- デモ用データの作成方法と削除方法を、開発・テスト環境に限定して用意する。

完成条件：必要な設定、起動方法、型チェック、テスト、ビルドの実行方法がREADMEにあり、各コマンドが現在の環境で実行できる。未設定の外部サービスは画面上でも開発者の出力でも識別できる。

#### B　DBと匿名所有権

実施すること：

- Part 4のテーブル・インデックス・制約・アクセス制御を実装する。
- Supabase SSR Authで検証したUIDを、DBの同一トランザクション内に限定して設定する。DB接続はBFF用の非所有者・`NOBYPASSRLS` ロールとする。
- 閲覧時は認証を発行せず、投稿を始める際に匿名セッションを用意する。
- サーバーが検証した所有者だけが自分の絵馬を編集できるようにする。
- 原子的な作成と、同一所有者・同一枠の競合を扱う。

完成条件：2つのUIDを使った所有権確認、同じ枠への競合、同じUIDによる複数枠の同時作成をDBを含めて検証する。プールされた接続の再利用で、前の利用者の認証文脈を残さない。

#### C　絵馬の作成と本人管理

実施すること：

- 文字入力、公開設定、プレビュー、投稿確定をつなぐ。DのCanvas実装前は番号・座標の簡易な場所選択で成立させる。
- 本人の編集・削除、編集競合、再送、通信切断からの復帰を実装する。
- 任意のメールOTPによる所有権の引継ぎ・復帰を実装する。
- anonymousから引継ぐ際に、別の所有者へ絵馬が複製されないようにする。

完成条件：画面を再読み込みしても保存した自分の絵馬が取得できる。第三者による更新が拒否され、文字や公開設定が失われずに再試行できる。

#### D　地図と探索

実施すること：

- Canvasの移動・ズーム、チャンク取得、集計表示を実装する。
- 一覧表示、番号からの移動、ランダム訪問、自分の絵馬への移動を用意する。
- 取得中・エラー・満員・受付終了を表示する。
- キーボードと一覧から利用できる経路を用意する。

完成条件：疎なworldと密なエリアの両方で使用でき、100万枠の全件取得をしない。場所と作品IDが区別され、削除したURLから別の作品が表示されない。

#### E　共有と近くへの招待

実施すること：

- 個別URL、OG、共有用PNG、X・LINEの共有入口、URLコピーを実装する。
- 投稿するSNS側の画面で本人が確定する。共有ボタンを押しただけで投稿済み扱いにしない。
- 近くへの招待から、候補選択・投稿・友達との位置関係の表示までをつなぐ。
- 本文を公開しない設定を、HTML・データ応答・OG・PNGのすべてに適用する。

完成条件：別のブラウザーで共有先を開き、公開範囲が一致している。招待を受けた人が自分の絵馬を掛け、同じworld内で両方を確認できる。

#### F　通報・運用・不正利用対策

実施すること：

- 通報、管理者の非表示・復帰、監査記録を実装する。
- 複数のサーバーインスタンスで共有する投稿回数制限を実装する。
- 本番の匿名登録に必要なCAPTCHA等の設定と、設定がない場合の扱いを明確にする。
- 利用者の入力をプレーンテキストとして扱い、操作権限のない更新を拒否する。

完成条件：一般利用者が管理APIを使えず、非表示操作後に本文が公開経路へ出ない。制限に達した際に新しい投稿が保存されず、再試行の案内が表示される。

#### G　性能・アクセシビリティ・回復

実施すること：

- 本パートの試験表を実行する。
- モバイルとデスクトップで、地図・作成・招待の主要経路を確認する。
- DB停止、通信切断、画像生成失敗、メールの遅延時の表示を確認する。
- 画像・データの配信量、API応答時間、操作中の描画を測る。

完成条件：公開を妨げる不具合が解消され、計測環境と結果、未解決の制約が記録されている。

#### H　公開環境の準備

実施すること：

- 公開環境の設定、worldの受付期間、サイトURL、問い合わせ先を確定する。
- デモデータや開発者専用機能を公開画面から除く。
- 監視、バックアップ、復旧、緊急に受付を止める手順を確認する。
- 独立した参加型サービスであること、公開範囲、保存期間の説明を実際の挙動に合わせる。

完成条件：公開環境を対象に投稿・共有・本人編集・削除・通報の流れを確認できる。テスト投稿は明示して管理し、実績の件数として残さない。

### 7. 性能の初期目標

以下は設計時の目標値。達成済みの保証として表示しない。計測結果を見て、描画の粗さ、配信量、環境費用を調整する。

| 項目 | 初期目標 | 測り方 |
|---|---|---|
| 公開ページの初期表示 | モバイルでLCP 2.5秒以下を目標 | 代表的なページ・端末・通信条件を記録。実利用データが得られればp75を見る |
| 地図の移動 | 代表的なスマホで継続30fps以上を目標 | 密なエリアを10秒移動しフレーム時間を記録 |
| 投稿確定API | stagingで20同時利用時のp95が2秒未満を目標 | メール送信時間を混ぜず、DBへの確定完了までを計測 |
| 地図データ | 通常の1チャンク応答のJSONが512 KiB以下を目標。保護上限は4 MiB | 最大400件、入力のバイト上限を含めて非圧縮サイズと同時取得数を記録 |

「通常の4G」「一般的なスマホ」とだけ記録しない。実際の端末名またはエミュレーション条件、ブラウザー、CPU・回線制限、サーバー地域、データ件数を記録する。

### 8. アクセシビリティと日本語表示

- 主要な操作のタップ領域は44×44 CSS px以上を設計目安にする。
- フォームにはラベル、入力例、文字数、エラーの関連付けを用意する。

### 9. P1・P2へ進むときの追加確認

#### P1　共同エリアと成就報告

- 同じworld内の配置・所有数・公開範囲のルールを維持する。
- グループ主催者であることを理由に、他人の非公開本文を取得できない。
- グループ一覧から外す操作と、絵馬そのものの削除を混同しない。
- 参加リンクから、一般の招待と同様に権限・枠競合を確認する。
- archivedのworldへ新たに参加できない。`ENABLE_GROUPS` と `ENABLE_FULFILLMENT` が無効なら、画面だけでなく対応APIも利用を拒否する。
- 成就報告は状態と更新日時だけを保持し、報告本文・写真・コメントは追加しない。所有者だけが状態を変更・取消でき、元の本文と公開設定を維持する。
- archivedでは成就状態を変更できない。成就後の共有画像にも元の公開設定を適用する。

#### P2　課金

- 価格・商品ID・購入対象をサーバー側で決め、ブラウザーから送った価格を信用しない。
- 決済の戻りURLだけで購入済みにせず、署名を検証したWebhookまたは決済サービスの確定情報で権利を付与する。
- Webhookの二重配送、順序の逆転、失敗後の再送を確認する。
- 支払い済みなのに権利付与が失敗した場合に、再実行して回復できる。
- 購入者が他人の絵馬へ有料デザインを付けたり、他人の企画を操作したりできない。
- 返金・失効後の表示と権利の扱いを明確にする。
- 本番決済の前にテストモードで成功・失敗・キャンセル・再送を確認する。
- `ENABLE_PAYMENTS=false` のときは決済の新規開始をサーバー側で拒否する。既存の決済結果の照合・返金・問い合わせ対応まで一律停止しない。

商品・金額・提供期間の詳細は [Part 6](#part-06) に従う。

### 11. Codexの完了報告

1. 実装した範囲と、対応した仕様の章。
2. 変更した主なファイルとDB変更。

### 3. 推奨するコードの分け方

ディレクトリ名は既存構成に合わせて変更してよい。次の責務を分離する。

- `app/`: 画面、ルート、メタ情報。APIの権限ロジックを画面コンポーネントへ埋め込まない。
- `domain/`: world、座標、入力制約、公開DTO、状態遷移、エラーコード。
- `server/`: Auth検証、DBトランザクション、公開投影、画像生成、レート制限。
- `features/world/`: カメラ、Canvas、チャンク取得、一覧代替。
- `features/ema/`: 入力、プレビュー、本人編集、公開設定。
- `features/sharing/`: SNSリンク、コピー、PNG保存、招待。
- `supabase/migrations/`: 再現可能なschema・権限・制約の変更。
- `tests/`: ドメイン検証、DB統合、重要なE2E。実装をなぞるだけのテストを増やさない。
- `docs/`: 運用、設定、実装状況、判断記録、本仕様書。

公開APIと画像生成は同じ `PublicEma` 投影を使う。owner_only本文を隠す処理を各画面に個別実装せず、サーバーの一箇所で公開可能な情報を決める。

### 4. 設定の分類

環境変数名は初期案。既存リポジトリやSDKの推奨名に合わせる場合も、公開・秘密の分類を維持する。

| 設定 | 公開可否 | 用途・不足時 |
|---|---|---|
| `APP_ORIGIN` | URL自体は公開可、設定はサーバー管理 | 正規URL、認証の戻り先、決済の戻り先。実在未確認のドメインを決め打ちしない |
| `NEXT_PUBLIC_SUPABASE_URL` | 公開可 | 認証接続先 |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | 公開可 | SDKの公開用キー。秘密キーの代用を入れない |
| `DATABASE_URL` | 秘密 | アプリ用の限定DBロール。ブラウザへ渡さない |
| migration用接続 | 秘密 | DDL用。通常のAPI実行時と分離 |
| CAPTCHA設定 | site keyのみ公開可 | 匿名作成等の不正利用対策。秘密の検証キーはサーバーだけ |
| レート制限用HMAC秘密 | 秘密 | 必要な場合の短期識別子。本文やメールをログへ残さない |
| `ENABLE_GROUPS` | 判定結果のみ公開可 | P1。既定false |
| `ENABLE_FULFILLMENT` | 判定結果のみ公開可 | P1の「願いが叶った」状態。既定false。決済の権利付与とは別 |
| `ENABLE_PAYMENTS` | 判定結果のみ公開可 | P2の新規販売。既定false。既存注文の照合を停止しない |
| Stripeの秘密鍵・Webhook署名秘密 | 秘密 | P2だけ。テスト/本番を分離 |
| Stripe Price IDと商品表 | サーバー管理 | 06のSKU・価格・対象期間との照合 |
| `featured_world_slug` | 公開可 | サーバー管理の設定。トップで案内する年 |
| 運営者名・問い合わせ・保存方針 | 公開情報 | ローカルは未設定表示可。本番では実際の情報が必要 |

`.env.example` は項目名と説明だけにし、実値を入れない。必須値がない環境では、何が不足しているかを開発ログで示し、利用者には秘密を出さない。無料公開に不要なStripe設定の欠如でP0を起動不能にしない。

### 5. 保存・削除・運用について決めること

P0の削除処理は04のとおり、稼働DBの本文と名前を消去し、公開投影から除く。UUIDの再利用を防ぐ最小記録は残す。

バックアップ、アクセスログ、監査、通報、決済記録には別の保存期間がある。採用するホストと運営方針に合わせて設定し、公開するプライバシー説明と一致させる。「削除した瞬間に全バックアップやSNS上から消える」とは案内しない。バックアップから復旧するときは、復旧時点以降の削除・公開範囲縮小・非表示を再適用する手順を用意して、公開取り消し済みの内容を再公開しない。復旧中は公開配信を止め、これらの再適用を確認できない作品は公開しない。削除等の最小記録をどう保全するかを復旧手順に含める。

初期公開前に埋める項目は以下とする。未確定でもローカル実装やテスト用の値で検証を進める。

| 項目 | いつ必要か | 未確定時の扱い |
|---|---|---|
| 本番ドメイン・HTTPS | 公開前 | `APP_ORIGIN` をローカルURLにして開発 |
| 公開日・world受付期間 | 公開前 | 01の案をseedとして検証 |
| 運営連絡先・公開文書 | 公開前 | 仮情報を本番へ出さず、設定不足として検出 |
| 作品・バックアップ等の保存期間 | 公開前 | 無期限・永久保存を約束しない |
| 通報対応者・管理者設定 | 公開前 | テスト用管理者で権限確認 |
| メール送信の設定 | 復元機能の公開前 | ローカル受信箱等でフローを検証 |
| 実売価格・商品・返金条件 | P2販売前 | 06の案をテストモードだけで使用 |
| 決済口座・販売者情報 | P2販売前 | 新規販売を無効のまま維持 |

### 7. 実装時の変更ルール

公開範囲の拡大、枚数制限、場所の独占、無料機能の有料化、保存期間、実売価格を変更するときは仕様を更新する。コード上の都合だけで意味を変えない。

色・余白・部品分割・小さな描画最適化は、体験と契約が変わらなければ実装者が調整してよい。07の数値目標を満たさない場合は測定結果と原因を記録し、調整した値を仕様にも反映する。

本書のSQLは設計断片であり、完成済みのmigrationではない。Codexは対象DBで制約と権限を実行検証し、再現可能なmigrationと検証結果を納品する。
