# Part 7　実装順序と品質確認

このパートは、Codexが実装を進める順序、各段階の完成条件、公開前に確認する動作を定義する。P0を一度に作り切ろうとせず、動く範囲を増やしながらデータの整合性と公開範囲を検証する。

## 1. 実装の原則

- 機能・権限・APIの矛盾は、[Part 4](04_DATA_AUTH_API.md) の契約へ戻って解消する。文言だけで不具合を隠さない。
- テスト用データ、接続のない画面、実DBへ保存した状態を区別する。
- 実際に保存できていないのに、投稿・メール送信・購入・共有の成功を表示しない。
- 型チェック・静的解析に加えて、投稿から取得までの実際の経路を確認する。
- サービスの外観を似せるだけのテストを増やさない。同時投稿、権限、公開範囲、再送、主要な利用の流れを優先する。
- 複数のブラウザー利用者は、異なる認証セッションで確認する。同じログインの別タブだけでは権限の確認にならない。
- 外部サービスをまだ設定できない場合も、データ契約とローカルの検証を進め、未接続項目と残った検証を正確に記録する。

## 2. P0の段階別実装

### A　土台と契約

実施すること：

- Next.js・TypeScriptのプロジェクト、フォーマット、型チェック、ビルド手順を用意する。
- world、絵馬、公開DTO、所有者DTO、エラーの型を定義する。
- 環境変数の例を値なしで用意し、秘密鍵をクライアントへ含めない構成にする。
- `2027` worldとデザイン `basic_wood` を設定から扱えるようにする。
- `ENABLE_GROUPS=false`、`ENABLE_FULFILLMENT=false`、`ENABLE_PAYMENTS=false` をサーバー設定の正本とし、クライアントには秘密を含まないcapabilitiesだけを渡す。
- デモ用データの作成方法と削除方法を、開発・テスト環境に限定して用意する。

完成条件：必要な設定、起動方法、型チェック、テスト、ビルドの実行方法がREADMEにあり、各コマンドが現在の環境で実行できる。未設定の外部サービスは画面上でも開発者の出力でも識別できる。

### B　DBと匿名所有権

実施すること：

- Part 4のテーブル・インデックス・制約・アクセス制御を実装する。
- Supabase SSR Authで検証したUIDを、DBの同一トランザクション内に限定して設定する。DB接続はBFF用の非所有者・`NOBYPASSRLS` ロールとする。
- 閲覧時は認証を発行せず、投稿を始める際に匿名セッションを用意する。
- サーバーが検証した所有者だけが自分の絵馬を編集できるようにする。
- 原子的な作成と、同一所有者・同一枠の競合を扱う。

完成条件：2つのUIDを使った所有権確認、同じ枠への競合、同じUIDによる複数枠の同時作成をDBを含めて検証する。プールされた接続の再利用で、前の利用者の認証文脈を残さない。

### C　絵馬の作成と本人管理

実施すること：

- 文字入力、公開設定、プレビュー、投稿確定をつなぐ。DのCanvas実装前は番号・座標の簡易な場所選択で成立させる。
- 本人の編集・削除、編集競合、再送、通信切断からの復帰を実装する。
- 任意のメールOTPによる所有権の引継ぎ・復帰を実装する。
- anonymousから引継ぐ際に、別の所有者へ絵馬が複製されないようにする。

完成条件：画面を再読み込みしても保存した自分の絵馬が取得できる。第三者による更新が拒否され、文字や公開設定が失われずに再試行できる。

### D　地図と探索

実施すること：

- Canvasの移動・ズーム、チャンク取得、集計表示を実装する。
- 一覧表示、番号からの移動、ランダム訪問、自分の絵馬への移動を用意する。
- 取得中・エラー・満員・受付終了を表示する。
- キーボードと一覧から利用できる経路を用意する。

完成条件：疎なworldと密なエリアの両方で使用でき、100万枠の全件取得をしない。場所と作品IDが区別され、削除したURLから別の作品が表示されない。

### E　共有と近くへの招待

実施すること：

- 個別URL、OG、共有用PNG、X・LINEの共有入口、URLコピーを実装する。
- 投稿するSNS側の画面で本人が確定する。共有ボタンを押しただけで投稿済み扱いにしない。
- 近くへの招待から、候補選択・投稿・友達との位置関係の表示までをつなぐ。
- 本文を公開しない設定を、HTML・データ応答・OG・PNGのすべてに適用する。

完成条件：別のブラウザーで共有先を開き、公開範囲が一致している。招待を受けた人が自分の絵馬を掛け、同じworld内で両方を確認できる。

### F　通報・運用・不正利用対策

実施すること：

- 通報、管理者の非表示・復帰、監査記録を実装する。
- 複数のサーバーインスタンスで共有する投稿回数制限を実装する。
- 本番の匿名登録に必要なCAPTCHA等の設定と、設定がない場合の扱いを明確にする。
- 利用者の入力をプレーンテキストとして扱い、操作権限のない更新を拒否する。

完成条件：一般利用者が管理APIを使えず、非表示操作後に本文が公開経路へ出ない。制限に達した際に新しい投稿が保存されず、再試行の案内が表示される。

### G　性能・アクセシビリティ・回復

実施すること：

- 本パートの試験表を実行する。
- モバイルとデスクトップで、地図・作成・招待の主要経路を確認する。
- DB停止、通信切断、画像生成失敗、メールの遅延時の表示を確認する。
- 画像・データの配信量、API応答時間、操作中の描画を測る。

完成条件：公開を妨げる不具合が解消され、計測環境と結果、未解決の制約が記録されている。

### H　公開環境の準備

実施すること：

- 公開環境の設定、worldの受付期間、サイトURL、問い合わせ先を確定する。
- デモデータや開発者専用機能を公開画面から除く。
- 監視、バックアップ、復旧、緊急に受付を止める手順を確認する。
- 独立した参加型サービスであること、公開範囲、保存期間の説明を実際の挙動に合わせる。

完成条件：公開環境を対象に投稿・共有・本人編集・削除・通報の流れを確認できる。テスト投稿は明示して管理し、実績の件数として残さない。

## 7. 性能の初期目標

以下は設計時の目標値。達成済みの保証として表示しない。計測結果を見て、描画の粗さ、配信量、環境費用を調整する。

| 項目                 | 初期目標                                                      | 測り方                                                                  |
| -------------------- | ------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 公開ページの初期表示 | モバイルでLCP 2.5秒以下を目標                                 | 代表的なページ・端末・通信条件を記録。実利用データが得られればp75を見る |
| 地図の移動           | 代表的なスマホで継続30fps以上を目標                           | 密なエリアを10秒移動しフレーム時間を記録                                |
| 投稿確定API          | stagingで20同時利用時のp95が2秒未満を目標                     | メール送信時間を混ぜず、DBへの確定完了までを計測                        |
| 地図データ           | 通常の1チャンク応答のJSONが512 KiB以下を目標。保護上限は4 MiB | 最大400件、入力のバイト上限を含めて非圧縮サイズと同時取得数を記録       |
| 広域描画             | 全件取得せず集計で表示                                        | ネットワークとクエリ件数を確認                                          |
| 障害時               | 下書き保持と再試行経路が動く                                  | 通信遮断・DB失敗を注入して確認                                          |

性能確認には空のworld、公開絵馬が1,000件のworld、特定地域が密なworldを使う。必要なら使い捨てのテスト環境でデータ量を増やす。100万枠の性能を、100万件の本番投稿を作る方法で確かめない。

「通常の4G」「一般的なスマホ」とだけ記録しない。実際の端末名またはエミュレーション条件、ブラウザー、CPU・回線制限、サーバー地域、データ件数を記録する。

## 8. アクセシビリティと日本語表示

- 代表幅360px・390px・768px・1440pxで確認する。地図の横幅とフォームの横幅を混同しない。
- 主要な操作のタップ領域は44×44 CSS px以上を設計目安にする。
- フォームにはラベル、入力例、文字数、エラーの関連付けを用意する。
- エラーは色だけに依存せず、どこを修正するか分かる文章で示す。
- フォーカスが見え、ダイアログから戻った後に元の操作位置へ戻る。
- 読み上げで「書く・プレビュー・投稿・共有・本人管理」へ到達できる。
- 動きを減らす設定を尊重する。音はP0の必須機能にしない。
- 日本語の句読点、改行、長い英数字、絵文字でレイアウトが壊れない。
- Canvasの本文が小さい場合でも、HTMLの詳細画面で全文を読める。

## 9. P1・P2へ進むときの追加確認

### P1　共同エリアと成就報告

- 同じworld内の配置・所有数・公開範囲のルールを維持する。
- グループ主催者であることを理由に、他人の非公開本文を取得できない。
- グループ一覧から外す操作と、絵馬そのものの削除を混同しない。
- 参加リンクから、一般の招待と同様に権限・枠競合を確認する。
- archivedのworldへ新たに参加できない。`ENABLE_GROUPS` と `ENABLE_FULFILLMENT` が無効なら、画面だけでなく対応APIも利用を拒否する。
- 成就報告は状態と更新日時だけを保持し、報告本文・写真・コメントは追加しない。所有者だけが状態を変更・取消でき、元の本文と公開設定を維持する。
- archivedでは成就状態を変更できない。成就後の共有画像にも元の公開設定を適用する。

### P2　課金

- 価格・商品ID・購入対象をサーバー側で決め、ブラウザーから送った価格を信用しない。
- 決済の戻りURLだけで購入済みにせず、署名を検証したWebhookまたは決済サービスの確定情報で権利を付与する。
- Webhookの二重配送、順序の逆転、失敗後の再送を確認する。
- 支払い済みなのに権利付与が失敗した場合に、再実行して回復できる。
- 購入者が他人の絵馬へ有料デザインを付けたり、他人の企画を操作したりできない。
- 返金・失効後の表示と権利の扱いを明確にする。
- 本番決済の前にテストモードで成功・失敗・キャンセル・再送を確認する。
- `ENABLE_PAYMENTS=false` のときは決済の新規開始をサーバー側で拒否する。既存の決済結果の照合・返金・問い合わせ対応まで一律停止しない。

商品・金額・提供期間の詳細は [Part 6](06_MONETIZATION_ROADMAP.md) に従う。

| 計測         | 願い本文や個人情報を解析イベントに送らない                                                                                               |

問題発生時は新規投稿の受付を止められるようにする。停止理由と再試行の案内を表示し、既存の絵馬閲覧や本人の削除操作は可能な範囲で維持する。

## 11. Codexの完了報告

各段階の終了時に、次を短く記録する。

1. 実装した範囲と、対応した仕様の章。
2. 変更した主なファイルとDB変更。
3. 実行した確認・結果・計測条件。
4. 未実装、外部設定待ち、確認できなかった項目。
5. 次に着手する段階と、残っている判断事項。

外部設定待ちの項目を「完了」とまとめない。仕様を変えた場合は、理由と影響範囲を記録し、関連するパートも同時に更新する。
