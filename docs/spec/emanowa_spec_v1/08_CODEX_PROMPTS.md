# Part 08 — Codexへの段階別指示

## 1. 渡し方

このフォルダの全パートを `docs/spec/` に配置する。まず「初回指示」を渡し、その後は必要な段階の指示を使う。関連パートを読むために全ファイルをリポジトリ内へ置く。分割して添付する場合も、00・04の共通契約を各回で参照できるようにする。

P0は07のA〜Hの順番で作る。P1/P2はP0の後。仕様の変更が必要なら、勝手に実装だけを変えず `docs/decisions.md` に理由と関連パートの変更を記録する。作業継続の情報は `docs/implementation-status.md` に残す。

## 2. 初回指示

```text
「えまのわ」という日本語のオンライン絵馬サービスを実装してください。
仕様は docs/spec/00_README.md から始まる複数のMarkdownにあります。

まず次を確認してください。
1. 既存リポジトリの構成、AGENTS.md、既存コード、依存関係、テスト、実行方法。
2. 00_README.md、01_PRODUCT_SCOPE.md、04_DATA_AUTH_API.md、
   07_QUALITY_IMPLEMENTATION.md。作業範囲に関係する他のパートも読む。
3. 既存の変更を壊さず、新規か既存拡張かを判断する。

今回の対象はP0です。初めに07の段階A「土台と契約」を実装してください。
新規ならNext.js App Router、TypeScript、Supabaseを仕様の初期案として使い、
実装時点の公式資料で互換性を確認して依存バージョンをlockfileに固定してください。
既存プロジェクトに構成がある場合は、その事情を確認して最小限で合わせてください。

100万の空白DB行・DOMを作らず、本文非公開・URL限定・本人の所有権を守ってください。
外部キーがなくてもスキーマ、migrations、型、画面、ローカル検証を進めてください。
モックは開発用と分かるようにし、本番保存の代わりにしないでください。
P1/P2の未完成ボタン、仮の支払い成功、架空の利用者数は公開画面に出さないでください。

実装後、変更点、実行方法、実行した検証、その結果、未検証事項、次の段階を報告し、
docs/implementation-status.md に記録してください。
```

## 3. 段階A — 土台と契約

```text
07の段階Aを完成させてください。00・01・02・04を参照します。

アプリの起動、画面ルート、共通レイアウト、デザイン変数、ドメイン型、入力検証、
公開DTOと本人DTOの区別、設定検証、開発用seedの構成を整えてください。
設定例には実際の秘密情報を入れず、公開環境変数とサーバー専用変数を区別してください。
画面は日本語、スマートフォンを優先し、地図の一覧代替へ進める形にしてください。

この段階では地図・決済を作り込まず、後続が同じ型と契約を使える状態にしてください。
起動と主要ルートの表示を確認し、残る未実装部分を明示して報告してください。
```

## 4. 段階B — DBと匿名所有権

```text
07の段階Bを実装してください。04をDB・APIの正本として扱います。

world、ema、冪等記録、通報等のP0スキーマ、制約、索引、権限制御をmigrationsで作成し、
ローカル環境で初期化から再現できるようにしてください。
限定DBロール、transaction-localの認証文脈、Supabase匿名認証、
公開投影と本人用取得を実装してください。メール連携の完成は段階Cで扱います。
閲覧だけで匿名アカウントを作らず、所有者をクライアント入力から採用しないでください。

別ユーザーの読み書き拒否、公開情報だけの取得、匿名セッションの分離を
実際のローカルDB/Authを使って確認してください。
クラウド設定が未提供なら必要項目を手順化し、検証できた範囲を明記してください。
```

## 5. 段階C — 作成と本人管理

```text
07の段階Cを実装してください。02・03・04を参照します。

入力、プレビュー、場所選択、確定、本人の絵馬への復帰、編集・削除、公開設定を
フロントからDBまで接続してください。場所選択は、この段階では番号・座標の簡易UIで
成立させてよく、Canvas地図との統合は段階Dで行います。
メール連携とOTP復帰を完成させ、ゲストの所有UIDが変わらないことを確認してください。
同じ枠・同じ所有者への同時投稿、再送、編集version競合を扱い、
競合や通信失敗時に下書きを消さないでください。
保存確認がない状態で「掛けました」と表示しないでください。

DBを使う意味のある並行実行テストと、2ブラウザでの所有権・公開設定の確認を行い、
07の該当受け入れ条件を満たしたか報告してください。
```

## 6. 段階D — 地図と探索

```text
07の段階Dを実装してください。03を座標・描画、04をAPIの正本にします。

絵馬へのフォーカス、空き枠の選択、公開絵馬の一覧・新着・分類・ランダムを接続してください。

非公開本文やURL限定の識別子を地図データへ含めないでください。

四隅の座標変換、パンとクリックの区別、スマートフォンの操作、一覧代替を確認し、
指定の密度fixtureで測定値を記録してください。本番DBに負荷試験データを入れないでください。
```

## 7. 段階E — 共有と近くへの招待

```text
07の段階Eを実装してください。05のP0範囲と04を参照します。

owner_only本文、unlistedの扱い、削除後の画像、no-storeとアプリ内キャッシュの挙動を
公開ページ・メタ情報・画像・レスポンスで確認してください。

招待先が削除済み/満席/別年度/既に自分の絵馬がある場合も実装し、

```

## 8. 段階F〜G — 運用と品質

```text
07の段階F・Gを実装・検証してください。04の管理・制限契約にも従います。

通報、運営による非表示・復帰、役割確認、操作監査、共有されたレート制限、
必要なCAPTCHA、受付停止、障害時の回復導線を完成させてください。

本人だけの本文・名前・メール・認証情報をログや解析へ送らないでください。

07の機能・同時実行・公開範囲・障害・性能・アクセシビリティの条件を確認し、
実測値と未達項目、再現手順を記録してください。
テストを通すために仕様や制約を弱めず、発見した問題を修正してください。
```

## 10. P1を追加するとき

```text
P0の完成状況を確認したうえで、05・04・07に従ってP1を追加してください。

無料グループは同じ世界の10×10の非独占範囲、1絵馬につき1グループ、
1確認済み主催者につき1年度の有効グループ1つです。
既存の絵馬は範囲内なら参加でき、範囲外の絵馬を移動・複製しないでください。
主催者が他人の絵馬の所有者にならないよう、権限を分離してください。
願いが叶った記録は状態と時刻だけにし、追加本文・写真は実装しないでください。

P1 migrationとテストを追加し、公開範囲・退会・所属除外・満席・archiveを検証してください。
ENABLE_GROUPS/ENABLE_FULFILLMENTは検証後に対象環境で有効化してください。
```

## 11. P2を追加するとき

```text
P0/P1を維持しながら06・04・07に従ってP2を実装してください。
価格と販売期間は06の初期案を設定値にし、実際の販売前に運営設定で確定できる形にします。

商品定義、注文、Checkout、署名付きWebhook、重複排除、権利、注文照合、返金を
テスト環境で接続してください。成功ページだけで権利を付与しないでください。
商品を買っても絵馬の枚数・場所の排他性・秘密の本文の閲覧権限を増やさないでください。

二重クリック・再送・順不同・支払失敗・キャンセル・返金・再ログインを検証し、
ENABLE_PAYMENTSは実販売の設定と検証が揃うまでfalseを維持してください。
```

## 12. 各段階の完了報告形式

```text
対象段階:
実装した体験:
主な変更ファイル:
DB migration / 設定変更:
検証した経路と結果:
実行していない検証と理由:
仕様からの変更と理由:
既知の問題・外部設定が必要な項目:
次に実装する段階:
```

「ビルド成功」と「本人だけの本文が別ユーザーに漏れないことを確認」は別の検証である。実際に確認した内容だけを完了として報告する。
